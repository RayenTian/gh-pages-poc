Copying a LoRA-trained MoE model to the generation engine — and why the grouped experts arrived untrained

Companion illustration for NVIDIA-NeMo/RL #3353 (merge grouped-expert LoRA weights during refit). All permalinks pin the PR head 34451c1a93; upstream links pin the Automodel submodule at b916107a.

Before
With LoRA on Automodel's grouped MoE experts, the weight copy sent the expert adapters to the engine as unknown keys. The first copy crashed with KeyError: 'layers.0.moe.experts.lora_gate_and_up_A'; had it not crashed, generation would have run the experts without their trained update.
This PR
Folds each expert's adapter into the fused base weight before the copy, and leaves the adapter tensors out of the stream — so the engine gets the trained experts and nothing it cannot name.
Status
Fixed by this PR. A real GRPO run (a Gemma MoE model, 8×B200, merged refit) now trains with generation–training logprob gaps below the test threshold.
Background — what "refit" is. In RL training, the model is trained in one place and answers prompts (rollout) in another — a fast inference engine like vLLM. Every step, the fresh weights are copied from the trainer into the engine. That copy is the refit. If the copy hands over the wrong weights, the engine generates from a different model than the one being trained, and the two drift apart. Dotted words have a short explanation: hover or tap them.

With LoRA, the trainer does not hold one finished weight. It holds the frozen base weight W plus two small matrices A, B, and the real weight is W + A·B·scale. The refit exporter must hand the engine that combined weight. For ordinary nn.Linear layers it already does. The break was in how Automodel stores LoRA for grouped MoE experts, where all experts share one fused tensor and the adapters sit beside it as plain parameters — a shape the exporter's filter did not recognise. The figure shows what each of the module's six tensors became on the way to the engine, before and after this PR.

The numbers come from the tiny case in the fix section below: one expert, scale = 2, worked through both projections.

The fix: fold A·B into the base, in the experts' own orientation

Where the fix lands: RL only, one file. automodel_policy_worker.py. No Automodel change: the adapter math already lives upstream in lora_experts.py; this PR only teaches the exporter to reproduce it.

Two changes. First, the "is this an adapter?" test learns the four bare grouped-expert names, so they are skipped instead of streamed as unknown keys:

Second, when the exporter reaches a fused base weight, it folds that expert module's adapter into it — a per-expert batched matmul, done in fp32, without touching the training weights:

@@ automodel_policy_worker.py L357-L374 · _maybe_merge_lora_weight (new branch, runs first)
+    expert_module, expert_adapters = _grouped_expert_lora_adapters(module_map, fqn)
+    if expert_module is not None and expert_adapters is not None:
+        lora_a, lora_b = (                          # gather all experts under expert parallelism
+            adapter.full_tensor() if isinstance(adapter, DTensor) else adapter
+            for adapter in expert_adapters
+        )
+        delta = torch.bmm(                          # [E, in, r] · [E, r, out] = [E, in, out], same shape as W
+            lora_a.to(device=tensor.device, dtype=torch.float32),
+            lora_b.to(device=tensor.device, dtype=torch.float32),
+        )
+        merged = tensor.to(torch.float32) + delta * expert_module.scale
+        return merged.to(tensor.dtype)              # single fp32 round-trip, base weight untouched
     if not fqn.endswith(".weight"):
         return tensor

The orientation matters and is easy to get backwards. For a plain nn.Linear the stored weight is [out, in] and the merge is B·A; for grouped experts the fused weight is [E, in, out], so the merge is A·B with no transpose — exactly the order the upstream forward uses when it computes x·W + (x·A·B)·scale.

Worked through one expert, with scale = 2:

base W = [[1, 0],      A = [[1],   B = [[5, 3]]   # gate_and_up: in=2, r=1, out=2
          [0, 4]]       [0]]

A · B        = [[5, 3],        # torch.bmm, per expert, fp32
                [0, 0]]
delta·scale  = [[10, 6],       # × scale (2)
                [0,  0]]
merged = W + delta·scale = [[11, 6],   # this is what the engine gets for this expert
                            [0,  4]]

A third change keeps the path honest: the reachability guard now also covers grouped experts, so if a future module wrapper renames these weights the refit raises loudly instead of silently shipping untrained experts again.

So what. Before this PR, LoRA on Automodel grouped experts could not be used with merged refit at all — the run died on the first weight copy. Worse than the crash was the near miss: if the keys had lined up, training would have "worked" while generation quietly ran the experts with their untrained weights, showing up only as a slowly widening training–generation gap many steps later. The merge closes both doors, and the gap on a real 8×B200 GRPO run stayed below the existing test threshold.
