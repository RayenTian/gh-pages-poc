Before
Two ways to swap the worker, with different rules. A config value was rejected whenever quant_cfg was set, even if it was the right worker. A constructor argument skipped that check.
This PR
The config value becomes the only path. One shared function decides the worker and checks it against quantization. The constructor argument still works but warns, and feeds the same function.
Status
Fixes the gap, still in review. Not merged. Lint and other quick checks pass; the GPU CI has not run yet.
Background: the words on this page Dotted words have a short explanation: hover or tap them.
  • A worker class runs the model. The default one comes from the backend (Megatron, Automodel, vLLM sync or async).
  • worker_extension_cls_fqn lets a user swap in their own subclass.
  • quant_cfg turns on quantization, which needs a matching quantized worker.

One shared function, resolve_worker_cls, now decides the worker for both the policy and vLLM. It takes the default class, the config, and the quantized class (or None when quantization is off). If quantization is on and the config names nothing, it fills in the quantized worker and warns. If the config names exactly that worker, it accepts. If it names anything else, it raises before any GPU is allocated.

Same four inputs, before and after

Two rows matter most. Row D was the bug in issue #4032: the right class, written by hand, was refused. Row C was the hole: a class passed in code skipped the quantization check, so a custom worker could run with quant_cfg set and no check that it was the quantized one. Rows A and B behave as before, except that A now warns and B now names the class you need.

The first hunk removes the blanket "mutually exclusive" error and turns the constructor argument into a config write. The second sends every decision through the shared function. Around those two:

• Policy and VllmGeneration now check that the final worker is in the environment registry before they allocate GPUs, even for default workers (lm_policy.py L344, vllm_generation.py L389).
• SFTv2 now sets the config field to its worker and refuses any other value (sft_v2.py L575-L581). The research template moved the same choice into its YAML (L95).
• A frozen teacher drops the copied field, so it always runs the plain Megatron worker (teacher_worker_group.py L219).

Break to know about (this is the ! in the title). With quant_cfg set, a custom subclass is now refused on both paths: the config and the constructor. Before, the constructor path let it through. Without quantization, custom workers work as before. SFTv2 likewise accepts only its own worker, not a subclass of it. Old quantized recipes that leave the field empty keep working; they just print a warning with the class to write down.
