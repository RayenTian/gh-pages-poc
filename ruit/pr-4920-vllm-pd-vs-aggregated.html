One request, two engines: how vLLM prefill/decode split differs from one engine doing both

Before
With vLLM, one engine reads the whole prompt and then writes the answer. Only TRT-LLM could split those two jobs across engines.
This PR

vLLM split vs one enginethree backends compared

Two pages on this work, one question each. This one: how the vLLM split differs from one engine doing both.

Background: the words on this page A language model serves a request in two jobs. Prefill reads the prompt. Decode writes the answer. Today one engine does both. This PR lets two engines share the work, and moves the stored prompt state between them with NIXL. The caller is NeMo Gym. Dotted words have a short explanation: hover or tap them.

With the split on, Gym still talks to one address, as before. That address is now a relay() server instead of an engine. It makes two engine calls where there used to be one. Everything else about the reply looks the same to Gym.

What goes over the wire, side by side

Steps in order: ① Gym sends a normal chat request. ② The frontend forwards it to a prefill engine with max_tokens: 1, because vLLM only runs a request that makes at least one token. The engine keeps the prompt's cached state and answers with a handshake (kv_transfer_params). ③ The frontend puts that handshake into a second request for a decode engine. ④ The decode engine pulls the cached state straight from the prefill engine's GPU. ⑤ It writes the answer, and the frontend returns it to Gym.

Where the two paths become one

The decode leg ends in the same engine route that serves every request today, create_chat_completion. To that route it is an ordinary chat request. It only carries two extras: the handshake and the prompt ids the prefill engine used (build_decode_leg). So sampling, tool parsing and the reply format are the same code in both modes.

Still different after that pointWhat happens
Prompt idsThe frontend can render the prompt itself (frontend_tokenize) and checks it against the engine's own render on a sample of requests. The aggregated path always renders inside the engine.
Weight updates (refit)The driver pauses prefill engines first, then decode; it resumes decode first, then prefill (pause, resume). The frontends must be told the engines are ready again after every refit.
Between stepsFrontends drop their stored handshakes and every engine releases the blocks its connector still holds before the prefix cache is reset. The PR says this reset must succeed.
Session idNeMo RL turns on Gym's forward_session_id_as_conversation_id, so the frontend can send a conversation's turns to the same prefill engine.

Why keep both, and what the split costs

  • Why split: prefill and decode stress the GPU in different ways, so each role can get its own engine count and parallelism. This is the same idea as the TRT-LLM design in #4095; both now share one layout planner, disagg_layout.py.
  • What it costs: a second hop per request, CPU frontend actors to run, and a longer list of setup rules. It needs async_engine and expose_http_server, so it works only on the NeMo-Gym rollout path. The PR refuses it together with dynamo or several HTTP servers per engine.
  • Evidence in the PR: two 100-step runs on 2 GB200 nodes (Qwen3-1.7B, split vs not split) learn at the same pace; step time medians are 7.2 s and 7.7 s. The PR itself says this is not a throughput measurement, and the runs keep both roles on one node.
So what. For Gym nothing changes: same address, same reply. The risk sits in the new middle layer. Its two calls, its handshake and its refit ordering are the parts to read closely in review. The aggregated path stays the default.
