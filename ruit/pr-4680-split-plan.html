三、如何提取、验证并逐个合并

分支与补丁操作

  1. 保留原 head 作为只读功能基准，不重写原作者分支。
  2. 从最新实际目标分支建立拆分分支；按功能抽取 hunks，历史修复 commit 只作为定位线索。
  3. 先准备 01、04、05、06，形成可用基线；02/03 独立评审。
  4. 后续使用 stacked branches。每次合并前确认前置依赖已合入目标分支，再更新 base，去掉重复 diff。
  5. 建立逐项归属清单：每个行为、配置键、测试、文档和辅助修改都有归属，避免遗漏或重复。
  6. 每次触发 CI 前重新获取 PR head 和实际目标分支；若落后，先 rebase、解决冲突、检查和 push，再对新的完整 SHA 触发 CI。

测试代码先复用搭建过程

  • 共享 TP/CP 建组、进程启动与清理、小张量、表与 alignment fixture、基础 config builder。
  • 共享禁止 rank-3 gather 的 patch/context manager，以及 IPC 记录构造和生命周期检查。
  • helper 随首个消费者落地，放在测试工具模块；避免从其他 test_*.py 导入纯 helper。
  • 相同执行逻辑的输入组合参数化，但保留各后端真实接入检查。
  • 删除只检查 Pydantic 默认值、类型约束、值原样返回的测试；复用 shipped-config sweep，不测试 recipe 字面参数值。
  • 参考计算保持独立。 loss、mask、梯度不能与被测实现共享同一套计算后互相证明。

三个验证层级

层级做什么能证明什么
CPU / Gloo toy独立参考、loss/梯度、mask、chunk、TP/CP 边界小输入上的算法与分片正确性
单节点 GPU smoke小模型、短序列，实际 optimizer update 与 validation；涉及状态的阶段保存恢复目标代码路径与实际后端接通；不等于收敛
Recipe qualification按正式 recipe 跑完，确定时间预算和 recipe 对应阈值，再登记 nightly该 recipe 的执行结果；不能只凭 finite loss 宣称收敛

测试不在专用 review checkout 中启动训练。实际 GPU 验证使用独立工作 checkout，通过现有 tools/launch 提交，遵守现有资源与日志规则。临时 instrumentation 用于证明路径激活，验证后移除。

最终接口与行为

  • 最终恢复原 PR 有效配置能力和默认行为：PR 06 使用 dense K=0；PR 08 才引入默认 K=128，并一直保留 dense 参考模式。
  • 有限 K 改变比较的 support，因此 dense/sparse 的一致性检查必须采用相同 support 设置。
  • 中间版本只公开已接通的能力，不提前塞入未来实现和 imports。
  • README、guide 随对应阶段扩展；完整 packing 设计文档放 PR 12。
  • 最终按功能与数值行为对照原 head，不要求文件逐字相同；已有审查中确认需修正的问题不因“保留功能”而被保留。

完成标准

  • 每个 PR 有清楚的行为边界、完整 producer/consumer 链路、针对性测试和明确限制。
  • 超过约 5,000 行的拆分 PR 再次检查是否混入后续能力。这是评审预算，不是拆分后的实测行数。
  • 最终运行配置检查、相关单测和代表性组合检查，逐项核对原 diff 的归属清单。
  • 仍需在提取实际 patch 后确认各 PR 可以独立合并；本页面没有把待验证的方案写成已完成结果。
