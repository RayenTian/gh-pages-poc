Scoring against the reference model without copying frozen LoRA weights

NVIDIA-NeMo/RL #5289 (Megatron backend, LoRA runs). All permalinks pin the PR head 5a1f4c1.

Background. Some losses (DPO, GRPO with a KL term) need the log-probabilities of a frozen reference model. Megatron does not keep a second model on the GPU. It keeps the reference weights in CPU memory and, for each scoring call, swaps them into the live model, scores, then swaps the policy back. With LoRA almost all weights are frozen and identical in policy and reference. Only the small adapters and a few buffers differ. Dotted words have a short explanation: hover or tap them.
Before
Every scoring call copied all weights to CPU and back, including the frozen ones that are the same on both sides. A failure during scoring also left the model holding reference weights.
This PR
With LoRA on, skips frozen parameters in all three places that touch the reference state. Also restores the policy, the sampling settings and the forward hooks if scoring fails.
Status
Performance change, same results. Full-model (non-LoRA) runs take the old path. The review found no bug that breaks it.

Same swap, fewer tensors

Three tensors stand in for the whole model: a frozen base weight, a LoRA adapter, and a buffer. Values are the ones the PR's own unit test uses, so the figure matches what the test checks. Policy: weight 1.0, adapter 3.0, buffer 2.0. Reference: weight 1.0, adapter 13.0, buffer 12.0.

What changed in the code

Where the fix lands: RL only, two files. setup.py decides what goes into the CPU reference copy; megatron_policy_worker.py decides what is backed up and written back. No Gym or Megatron-LM change.

The line marked - is from the parent commit; it no longer exists at the pinned head. keep_vars=True is what makes the test possible: a frozen LoRA base weight is a Parameter with requires_grad=False. Buffers and the _extra_state entries (for example FP8 scales) are not Parameters, so they are still swapped. Full-model runs have peft.enabled=False and skip nothing.

Before, the restore lines ran only after a normal yield, so an exception inside the with block left reference weights in the model. The forward-hook re-enable now also depends on the hook having been on at entry (:3374), so a hook that was already off is not switched on by the exit.

So what. On the author's measurement (Qwen3-0.6B, LoRA rank 32, one H100), CPU memory held for the reference copy and policy backup falls from 2,358.9 MiB to 85.2 MiB, and host–device traffic per scoring call from 3,538.4 MiB to 127.8 MiB. GPU memory is unchanged, and logged DPO training losses matched between the two runs. The gain grows with model size, because the skipped part is the frozen base. The skip trusts that a parameter frozen in the policy has the same value in the reference, which holds for LoRA.
