改动前
替换 worker 有两条路,规则不一样。config 里的值只要设了 quant_cfg 就被拒绝,哪怕填的正是正确的 worker;构造参数则完全跳过这项检查。
本 PR
config 里的值成为唯一路径。一个共享函数负责选 worker,并对照量化要求检查。构造参数仍可用,但会发出弃用警告,并把值交给同一个函数。
状态
补上了这个缺口,仍在 review 中。尚未合并。lint 等快速检查已通过,GPU CI 还没跑。
背景:本页用到的几个词 带虚线的词有简短解释:鼠标悬停或点按即可查看。
  • A worker 类负责运行模型。默认值由后端决定(Megatron、Automodel、vLLM 同步或异步)。
  • worker_extension_cls_fqn让用户换成自己写的子类。
  • quant_cfg开启量化,需要配套的量化 worker。

现在由一个共享函数 resolve_worker_cls 同时负责 policy 和 vLLM 的 worker 选择。它接收默认类、config 和量化类(没开量化时是 None)。开了量化而 config 没填:自动填入量化 worker 并发出警告。config 填的正好是量化 worker:通过。填了别的:在分配任何 GPU 之前就报错。

同样四种输入,改动前后对比

最重要的是两行。D 行就是 issue #4032 的 bug:手写了正确的类,却被拒绝。C 行是漏洞:在代码里传入的类会跳过量化检查,于是设了 quant_cfg 时,自定义 worker 也能跑起来,没人检查它是不是量化 worker。A、B 两行和以前一致,只是 A 现在会警告,B 现在会告诉你需要哪个类。

第一处 diff 去掉了一刀切的"互斥"报错,并把构造参数变成对 config 的写入。第二处让所有决定都经过共享函数。除此之外:

• Policy 和 VllmGeneration 现在会在分配 GPU 之前,检查最终选出的 worker 是否在 环境注册表里,默认 worker 也要检查(lm_policy.py L344, vllm_generation.py L389).
• SFTv2 现在把 config 字段设为自己的 worker,并拒绝其他任何值(sft_v2.py L575-L581)。research 模板把同样的选择移到了它的 YAML 里(L95).
• 冻结的 teacher 会丢掉复制来的该字段,因此始终使用普通的 Megatron worker(teacher_worker_group.py L219).

需要知道的不兼容变化(标题里的 ! 就指这个)。设了 quant_cfg 时,自定义子类现在在两条路径上都会被拒绝:config 和构造参数。以前构造参数那条路能放行。不开量化时,自定义 worker 照常可用。SFTv2 同样只接受它自己的 worker,不接受它的子类。字段留空的旧量化 recipe 仍能运行,只是会打印一条警告,告诉你该写哪个类。
