二、目录布局：今天与提议

今天（PR #4680 里）

  • 每个区域里，X-Token 和 CSD 各放在以方法命名的目录下。只有 nemo_rl/data/cross_tokenizer/ 已经同时放两者。
  • trainer 和 x_token/ 下的辅助代码两种方法都在用，名字却带着 X-Token。
  • run_csd.py 只是带着 csd.yaml 调用 X-Token 的入口。
  • PR 只改了一个文件的名字：使用指南，它现在同时讲两种方法。

提议：一个 runner、一个 trainer

  • 一个 runner 和一个 trainer 服务两种方法，名字不带方法名。
  • 每种方法保留自己的 loss 和工具，放在 cross_tokenizer 目录下。
  • 文件里的代码不变，只改名字、目录和指向它们的 import。

三、每个 PR 如何保持可以安全合并

每个 PR 都从当前的 main 切出，必须单独通过完整 CI 才能合并。

  • 任何 PR 都不调用还不在 main 上、也不在同一个 PR 里的代码，所以两次合并之间不会出问题。
  • X-Token 在每一步都可用。改到 X-Token 代码的 PR 还要跑两个 X-Token nightly。
  • PR 1 带来两项 X-Token bug 修复：使用 context parallelism（把一条序列切给多个 GPU）时的 teacher 打分，以及严格的 exact-map 规则。X-Token 的 nightly recipe 不受影响。
  • 新的 CSD recipe 按 main 现在的命名（-automodel-，不是 -dtensor-）。
  • PR #4680 变成冻结的 draft，只作参考。最后一块合入后把它关闭，不合并。如果 packing 暂缓，它就继续开着，作为 packing 的参考。

需要团队决定

  • 是否同意这个拆法；packing（PR 4）是现在合入，还是留在参考分支上。
  • 是否同意 PR 0 的布局：一个 runner 和一个 trainer，名字不带方法名；每种方法的 loss 和工具放在 cross_tokenizer 目录下。
