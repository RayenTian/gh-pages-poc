vLLM split vs one enginethree backends compared

Two pages on this work, one question each. This one: what each backend supports, and where the three designs differ.

Background Prefill reads the whole prompt and builds the KV cache. Decode then produces tokens one at a time. Splitting them means one engine does prefill, sends the KV cache to a second engine, and that one decodes. A replica is one group of such engines. Something has to sit in front of a replica and pick the two engines for each request. Who provides that piece is the main difference between the backends. Dotted words have a short explanation: hover or tap them.

All three backends read the same layout block, generation.disaggregation: on/off, prefill engines per replica, decode engines per replica. All three need separate training and generation GPUs and one pipeline stage. Past that point they differ. TRT-LLM and SGLang use the pairing server that ships with the engine. vLLM has none, so #4920 writes one inside NeMo RL. That choice decides how rollouts connect, which features exist, and how much code NeMo RL has to keep working.

Questions for the design discussion: nothing here is implemented

Nothing below is implemented. These are the places where the three backends made different choices that are not forced by the engines.

  1. Should the shared block hold only what all three use? DisaggConfig has six fields. SGLang uses three and rejects the other three (num_frontend_workers, frontend_tokenize, frontend_base_port). Those three could move to the backends that start their own front workers.
  2. One name per setting. The backend block has three names and the routing settings have three spellings (table rows 12 and 13). A user who switches backend has to relearn them. The vLLM and SGLang names are not released yet, so they are free to change today.
  3. One place for setup checks. Each backend checks in a different place, and the rules point in opposite directions: TRT-LLM and vLLM require NeMo-Gym, SGLang refuses it. One entry that every entrypoint calls and that asks the backend "which rollout path and which entrypoints do you support" would keep them from drifting.
  4. Finish the move to shared layout code. TRT-LLM still has its own copy of the engine planning, and SGLang has its own node-fitting rule because the shared one does not handle an engine wider than a node.
  5. Write the contract down. The design doc explains the design in TRT-LLM terms and adds the other two as extra sections. A table like the one above, kept in the doc, would say what a backend must provide and what it may leave out.
