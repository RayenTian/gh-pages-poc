Do not split by folder, and do not split by layer. One file takes part in several stages, especially csd.py, loss_utils.py and the training controller, so code must be extracted by function, branch and producer/consumer chain. Splitting by layer ("operators → loss → wiring into training") means the first pieces have no caller when they merge, so this plan splits by "changes to existing code", "tools that run on their own", "the smallest feature that runs", and "optional variants" instead.

Upstream Megatron-Core and Megatron-Bridge have long implemented it and use it in their bundled performance recipes; but NeMo-RL's own code that assembles the config and builds the model has never passed the switch down. In scope

  • Pass through reduce_scatter_with_fp32_accumulation.

When extracting

  • Where the new MoE router padding mask on the packed path belongs is undecided.

Acceptance

  • The ordinary Megatron load path still works; when the model and tokenizer sources differ, the specified tokenizer is the one loaded.

04Tools that build and validate the sub-token tablesStandalone tool · Depends on: the folder layout decided in PR 01; independent in code, can be reviewed in parallel

feat(csd): add bidirectional sub-token table tooling

Two offline scripts to run before CSD training. They use only tokenizers, load no model, and run on CPU.

In scope

  • The build script (303 lines): for every token in the source tokenizer's vocabulary, find the chain of tokens in the destination tokenizer that spells the same text. It produces one direction per run, so it runs once for student→teacher and once for teacher→student.
  • The validation script (144 lines): checks both tables against the two real tokenizers: whether the vocabulary sizes and tokenizer fingerprints match, whether the tensor structure is valid, and whether every row really spells the same text.
  • Notes on the table format, the fingerprint, and matching special tokens by role; unit tests.

Interface constraints

  • Keep the existing command-line arguments and output format.
  • Only tokenizers with a BPE model and a ByteLevel decoder are supported; other kinds fail with a clear error.
  • The token-chain length limit defaults to 8; longer chains are recorded as unmapped, not truncated.

Acceptance

  • Build, load and validate the two-way tables with the real Llama/Qwen tokenizers.
  • Invalid IDs, a wrong fingerprint and incomplete token chains fail clearly.
  • Recipe: not needed. Verified by unit tests with real tokenizers.

One thing left for PR 06 to decide

The fingerprint is checked only in the validation script. During training the CSD loss reads the table file directly and does not compare fingerprints. Skipping the validation script and training with a table from the wrong version is not caught. PR 06 must either compare at load time too, or make validation a required step in the guide.

Verified: the two scripts import only torch, tokenizers, transformers and each other, not nemo_rl; the training code does not import them either, so the two sides meet only through the file format. Scripts plus tests are about 700 lines.

05Code shared by both methods: loss base class, trainer, shared operators, teacher-logits transportChanges to existing code · Depends on: PR 01 · Direction settled, details still to work out

refactor(xtoken): extract shared cross-tokenizer loss base, trainer dispatch and teacher-logits transport

A good part of the original PR is not new CSD code. It reworks X-Token's existing loss, trainer and teacher-logits transport so they can hold a second method. The functions these changes sit in do not mention CSD. Make them an X-Token-only PR first; when it merges, X-Token uses all of it.

Why cut here

The X-Token loss already has two ways to compare (project everything and take a KL, or handle the one-to-one tokens first and then the rest), and they branch inside one method. The original PR's CSD loss was copied from the X-Token loss and then changed: the branch point becomes the CSD computation and the rest of the skeleton is the same. Of the methods with the same name in both classes, 4 are word-for-word or almost identical and another 5 are 0.7 to 0.85 similar, about 360 lines in each class. So CSD is closer to "a third way to compare inside the same framework" than to a separate, parallel algorithm.

In scope: the loss and trainer side

  • Extract a shared loss base class: multi-teacher aggregation (sum, averaged_logits, select_teacher), student CE, same-tokenizer KL, dynamic weights, metrics. The X-Token loss becomes a subclass that keeps only its own two ways to compare.
  • A dispatch point in the trainer that picks the loss and collator by method, with only the X-Token branch at this stage; plus the trainer's general changes that do not mention CSD (setup, validation, releasing shared GPU memory on failure) and their tests.
  • Base operators both methods need (such as the CP layout conversion), provided the X-Token path switches to them in this PR.

In scope: the teacher-logits transport side

  • The rework of the channel through which a teacher passes full-vocabulary logits to the student over shared GPU memory: a more compact storage format, zero-copy reads, and checks on shard coverage. Mostly in policy/utils.py (about 680 lines) and loss_utils.py (about 420 lines).
  • The read entry point rebuild_teacher_full_logits_from_ipc already exists on main and the X-Token loss uses it today, so when this rework merges its caller is X-Token.
  • If the read interface changes its return value, update every existing caller and test in this PR.

Boundaries of this stage

  • No CSD code and no CSD config keys.
  • Operators X-Token does not use stay out of this PR and go with the first PR that uses them.
  • Functions in the transport rework that only the Megatron worker calls wait for PR 09. How large that share is has not been verified.

Risk

The base class must take the CSD version of the implementation (a superset of the X-Token version; for example, cross-process sums use the process group passed in, not the global group), and the transport format changes too. This changes X-Token's code path. It is not a pure move and needs a before/after comparison.

Acceptance

  • On the same input, loss, gradients and metrics match item by item before and after the refactor.
  • All X-Token unit tests pass; the two X-Token nightlies are compared before and after the refactor.
  • Multi-teacher aggregation, student CE and same-tokenizer KL each have exactly one implementation in the repo.
  • Transport: shared GPU memory is really used, the zero-copy path is confirmed to be taken, and buffers are released when training fails too.
  • Recipe: none added. The two existing X-Token nightlies are the before/after comparison.

Rough estimate: 4,500 to 5,500 lines including tests, about 2,000 to 2,500 on the loss and trainer side and about 2,500 to 3,000 on the transport side. The two sides change different files and are both verified by the X-Token nightlies; if it proves too large in review, it can be split into two PRs reviewed in parallel, with no dependency in the way.

feat(csd): add single-teacher dense distillation on common tokens with Automodel

The CSD loss is the sum of two parts: a comparison on one-to-one tokens, and a comparison on mismatched chunks (for example one student token against several teacher tokens). The two parts are separate blocks in the core computation. This PR does only the first part; the second is in PR 07.

This PR delivers a simplified objective. It distills only on tokens both vocabularies share and ignores every mismatched chunk. It trains, validates, saves and restores end to end, but its effect differs from the full CSD. The full CSD objective starts at PR 07.

In scope

  • The CSD loss as a subclass of PR 05's base class: setup and chunk classification, the comparison on one-to-one tokens, and combining and scaling. Only the path the example config takes by default is implemented: JSD divergence, one-to-one tokens taken from the sub-token table, dynamic scaling.
  • The weight of mismatched chunks (csd_mismatch_loss_beta) must be 0; any other value is rejected at config validation.
  • A config field that chooses the method. It is required and has no default, so a CSD config that forgets it cannot quietly run as X-Token; each existing X-Token config on main gets one more line. The field's name and place are undecided.

  • The CE and KD combination; the remaining probability goes to REST.
  • The CSD collator; keep the text/chat mask and the truncation to the shared text prefix.
  • Base operators the loss needs come in with this PR: log-probabilities of selected tokens, chunked logsumexp, and a cross-process sum that carries gradients.
  • projection_matrix_path may be empty.
  • Training, validation, save and restore, and resource release on errors.
  • The example config csd.yaml is written as the Automodel version first (in the original PR it is the Megatron version) and changes at PR 09.

3. Final interface and completion criteria

Final interface and behavior

  • In the end the original PR's working config capabilities and default behavior are restored: PR 06 uses dense K=0; only PR 10 introduces the default K=128, and the dense reference mode is kept throughout.
  • A finite K changes the support being compared, so dense/sparse consistency checks must use the same support setting.
  • Intermediate versions expose only capabilities that are wired up, with no future implementations or imports put in ahead of time; values not wired up yet are rejected at config validation.
  • The README and guide grow with each stage; the full packing design doc goes in PR 14.
  • The end state is compared with the original head by feature and numerical behavior, not word for word by file; issues the existing review confirmed need fixing are not kept in the name of "preserving features".

Completion criteria

  • Every PR has a clear behavior boundary, a complete producer/consumer chain, targeted tests and stated limits; when it merges, the code it brings has a caller.
  • A split PR over about 5,000 lines is checked again for later capabilities mixed in. This is a review budget, not a measured line count after the split.
  • At the end, run the config checks, the related unit tests and checks on representative combinations, and go through the ownership list of the original diff item by item.
  • Whether each PR can merge on its own still has to be confirmed after the real patches are extracted; this page does not present a plan awaiting verification as a finished result.
