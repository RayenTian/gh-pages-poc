Two pages on this PR: what changes, then the confirmed custom-policy stall.

The fixed-weight policy waits for a complete batch from the oldest policy-weight version. Its admission gate allows only a bounded number of dispatches ahead of training. Both must progress for the run to continue.

Bounded CPU reproduction used the production factory, rollout pump, admission and selection with a fake buffer and generator. It observed one ready group, no shortfall credit, a closed gate, and a pending pump. No GPU training was run.

Why setup accepts it

The new guard rejects the name weight_fifo. The custom resolver can load the same repository-owned class under a different name, and the new admission check accepts its wait/commit methods. The class disables spare-pool replacements, so a filtered group takes the return-without-shortfall branch. The previous in-order-only guard rejected this configuration.

async_rl:
  min_groups_for_streaming_train: 2
  sampler:
    name: custom
    target: nemo_rl.algorithms.async_utils.staleness_sampler:WeightFifoSampler
    max_staleness_versions: 0

What would fix it — proposed, not in the PR

Nothing below is implemented. Make selection's complete-single-weight-batch requirement a required declaration on the policy class. Resolve custom classes before applying the DS rejection; inherited fixed-weight behavior must keep the same rejection. This needs changes to the sampler interface, class resolution and setup in this repository; no upstream library change is needed.

Require the declaration rather than silently assuming an unknown custom policy is compatible. Verify the exact class path above and an inherited policy in setup tests. Keep windowed behavior separate: it fills through ordinary dispatches, so crediting every no-pool policy would change its intended behavior.
