Dropping a flat-reward prompt group when token capture is on

Companion illustration for NVIDIA-NeMo/RL #5202 (dynamic sampling on the token-capture path), stacked on #4958. All permalinks pin the PR head 2a522a6.

1 · what it adds 2 · the broken test

Two pages on this PR — this one: the new capability and how it lines up with the path that already existed.

Two words first. Dynamic sampling drops a prompt group whose generations all scored the same reward. GRPO trains on how much better each answer is than the group's average, so a group with no reward spread gives every row zero advantage — it teaches the policy nothing. The controller throws it away and rolls a replacement prompt instead. Token capture is a second rollout path: the generator stages the heavy token tensors, then a separate finalizer actor assembles and verifies the group's rows before the group is allowed to become training data. The reward is final only after that verify step.
Before
Turning on both grpo.use_dynamic_sampling and token_capture.enabled was rejected at startup with a ValueError — the two could not run together.
This PR
Allows the combination. On the capture path the flat-reward drop runs inside the finalize step, right after the group's rows are verified, before the group becomes selectable.
Status
New capability. It extends the flat-reward drop that already ran on the non-capture path. (This page's sibling covers a test the change leaves broken.)

On the non-capture path the drop has always happened right after generation, inside rollout_manager.py generate_and_push :2670: the group is scored, and if its voting rewards carry no signal the reservation is removed and the call returns FILTERED. The capture path could not do that, because its rewards are not final until the finalizer has verified the rows. So this PR moves the same check into the finalize step (_finalize_with_actor :1582), and both paths decide which rows vote through one shared function, voting_rewards.

The _ZeroVarianceGroup is a sibling of #4958's _BelowValidFraction; both share a new _RejectedGroup base. The below-fraction check is kept first, so a group failing both is replaced from the fault-tolerance pool, not the filtering pool (:1553).

So what. A capture run can now throw away prompt groups that carry no learning signal, the same way a non-capture run already did — no more "disable one of the two." The price is only on the capture side: a dropped group has already done its token assembly and write, so if your zero_variance_fraction is high, each drop costs more than it would without capture. Size grpo.dynamic_sampling_max_gen_batches from the drop rate the run reports.
