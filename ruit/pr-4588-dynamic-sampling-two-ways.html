Dropping prompt groups that teach nothing: the old way, and the new single-controller way

Companion illustration for NVIDIA-NeMo/RL #4588 (enable single-controller dynamic sampling) and #1365. All permalinks pin the PR head 3bfe02f7.

Before
On the single-controller path, setup refused use_dynamic_sampling outright. The filter existed only in the older training loop.
This PR
Turns it on for the single-controller path, and replaces each dropped group one at a time instead of regenerating whole batches.
Status
Implemented in this PR — open, under review. Only the in_order sampler is supported; token capture and PPO are rejected at startup.
Background. In GRPO, one prompt is answered several times, and the group's rewards are compared against each other. If every answer in a group scores the same, there is nothing to compare, so every answer gets zero advantage and the group teaches the model nothing — it just costs generation time and a slot in the batch. Dynamic sampling (from DAPO) throws those groups away and gets more prompts instead. The two training loops below do that at completely different moments, which is the whole story on this page. Dotted words have a short explanation: hover or tap them.

The older loop filters after a whole batch has been generated and scored, so it can only react by generating another whole batch — and training waits. The single-controller path generates and trains at the same time, so it can react per group: it throws the group away before it reaches the buffer and sends one fresh prompt after it (rollout_manager.py:2160). Both end up training on the configured number of groups; they pay for it very differently.

The two paths, same five groups

Where the two meet, and what still differs

They converge on one thing only: the test for "this group teaches nothing". Both ask whether every reward in the group is exactly equal — exact equality, not a standard deviation near zero, because floating-point rounding can give a flat group a tiny spread. The rule is written twice, once per path:

older loop calculate_trivial_reward_distributions valid_rewards.numel() <= 1 or (valid_rewards.amin() == valid_rewards.amax()) single-ctrl rewards_carry_no_signal len(rewards) <= 1 or max(rewards) == min(rewards)

Same rule, different input. The older one is handed valid_mask and compares only the rows that will actually vote on the advantage; the new one compares every answer in the group. Under the default settings those are the same set, so the two agree. They part company when masked_reward_policy: exclude and overlong_filtering are both on, which is when the trainer stops counting rows whose answer was cut off — then the older path would drop a group that the single-controller path keeps.

Everything else is different, and the table is the short version:

older loop single-controller unit of replacement a whole generation batch one prompt group when it is decided after the batch is scored before the group is committed who waits the trainer, for a full batch nobody — the step borrows and moves on spare prompts none; it just generates more a pool set aside ahead of time the budget dynamic_sampling_max_gen_batches dynamic_sampling_max_replacements_per_slot counted per step counted per slot, default 32 over-generation knob batch_multiplier not read — has no effect here samplers n/a in_order only (or a custom one that marks which step a group is for)

One consequence worth stating on its own: every replacement on the new path is a prompt taken from the same dataloader, and the number of training steps a run can reach is bounded by how many batches the dataloader holds. So at a drop rate p, a run reaches roughly (1 − p) of the steps it was configured for and then stops cleanly. The older path has batch_multiplier to pay for that; the new path has no equivalent knob.

What you watch while it runs

Filtering changes what reward means. Only groups with spread get trained on, so the trained-rows average can sit flat while the model is in fact improving. The PR adds the pre-filter numbers next to it (rollout_manager.py:2022):

unfiltered_reward average over every group generated for the step, kept or dropped ← watch this one first_attempt_reward the same, but ignoring replacements generated_prompt_groups how many were generated for the step, dropped ones included zero_variance_fraction how many of them had no spread rollout/zero_variance_groups_total running count of groups actually thrown away
If you are turning this on. Pick the drop rate you expect and check it against zero_variance_fraction on a short run first — it decides both how many extra rollouts you pay for and how far short of max_num_steps the run will stop. Keep replacement_reserve_prompts at 1 or more, or the spare pool is never filled and every dropped group shrinks its step instead of being replaced. The sizing advice in the guide is the place to start, with the correction noted in the review.
