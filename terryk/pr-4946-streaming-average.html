How streaming training gets the right average when one step arrives in pieces

PR #4946 · refactor(loss) · permalinks pinned to d01c03a5

1 · one reducer 2 · streaming average

Two pages on this PR — this one: how the step that arrives in pieces gets the right average.

Before
Streaming training already existed. Each chunk trained with a divisor of 1, the worker added up token and response counts, and at the end of the step it picked one with its own copy of if loss_type == TOKEN_LEVEL.
This PR
The reducer from page 1 now counts each chunk and picks the end-of-step divisor. The logged loss and KL use that same divisor. MoE router losses under sequence_mean are now rejected at startup.
Status
Same gradients as before for both averages. The PR checked chunked against one-call training on GPU (DP2 and TP2, two optimizer steps). One new startup error, for a setup that used to train wrongly.

What "streaming" means here. In the single-controller loop, prompts are generated in groups (one prompt, several answers). The trainer does not wait for the whole step's batch. As soon as enough groups finish, it trains on them as one chunk, keeping the gradients without stepping the optimizer. When the step has enough groups, it divides the summed gradients once and steps. Chunk size is set by min/max_groups_for_streaming_train. Dotted words have a short explanation: hover or tap them.

The catch: the right divisor (all tokens in the step, or all responses) is only known after the last chunk. So every chunk divides by 1, and the worker keeps a running count.

One step, two chunks, one divide

Same example as page 1: response A has 4 tokens, B has 1, C has 6. A and B finish first and form chunk 1; C forms chunk 2. Shown for one DP rank; with more ranks, step ④ adds up every rank's counts.

QuestionAnswer
Who decides when a chunk is trained?The controller's _train_pump, as soon as the sampler can hand it enough finished groups.
What crosses to the GPUs?Row keys for each rank's slice (train_microbatches_from_meta). Each worker reads the token data from TQ itself.
Where does the reducer run?Inside each worker, made once per step in _split_step_state_init from the loss function it was given.
When is the divisor applied?Once, in finish_train_step, after one all-reduce of the counts and before the optimizer step.

What the PR changed on this path

Before

# Megatron worker, train_microbatch: once per chunk, on every DP rank
seqs += sum(sample_mask)
toks += sum(token_mask · sample_mask)
loss_fn(chunk, global_valid_toks=1, global_valid_seqs=1).backward()  # raw sums; grads add up
# finish_train_step: once per optimizer step
seqs, toks = all_reduce_over_DP([seqs, toks])
n = toks if loss_type == TOKEN_LEVEL else seqs                       # the 5th copy of the if
grads *= 1 / n;  optimizer.step()

After

# Megatron worker, train_microbatch: once per chunk, on every DP rank
seqs_c, toks_c, c = R.local_counts(chunk)                            # c = toks_c or seqs_c
seqs += seqs_c; toks += toks_c; objective += c
loss_fn(chunk, global_valid_toks=1, global_valid_seqs=1).backward()  # unchanged
# finish_train_step: once per optimizer step
seqs, toks, objective = all_reduce_over_DP([…])                      # still one collective
n = R.loss_divisor(toks, seqs, objective)                            # 11 or 3 in the example
grads *= 1 / n;  optimizer.step()
log loss, kl × 1 / R.loss_divisor(…)                                 # was: TOKENS or SEQUENCES

Real code: _train_microbatch_body, _finish_train_step_body. For token mean and sequence mean, objective always equals toks or seqs, and loss_divisor ignores it. It, and the StreamingObjectiveLoss wrapper, are there for the group average in #4947, whose divisor is neither count.

Why MoE router losses are rejected under sequence_mean

MoE models add small router losses that keep experts balanced. Megatron adds their gradients into the same layers during each chunk's backward pass. At the end, step ④ multiplies every gradient by 1/n. The router losses are summed over tokens, so they need n = tokens (token_normalized). Under token mean that is what they get. Under sequence mean they get n = responses: in the example, divided by 3 instead of 11, so about 3.7× too strong.

It cannot be fixed afterwards, because the router gradients are already mixed into the shared weights. MTP heads have the same problem but get a fix when they are detached, because then their gradients sit in their own weights. So the PR rejects nonzero moe_aux_loss_coeff (for an active balancing mode) or moe_z_loss_coeff under sequence_mean on this path.

So what. Streaming and one-call training give the same average and the same gradients, for both modes. The only change a user can hit: an MoE run with sequence_mean on the single-controller Megatron path now stops at startup instead of training with the router losses at the wrong strength. Set the router loss coefficients to 0, or use global_token_mean.
