Nine pages on this stack (#4905, #4979 and #5115), one question each. This one: what happens when one Dynamo frontend dies mid-run.

Before
One frontend (#4979). If it died, every Gym session retried it forever and the run stopped with no error. RL never checked it after startup.
This PR
Several frontends, each able to reach every engine. Each one still fails alone the same way: only its own sessions hang, but the step waits on them, so the run still stops. (With forest training, Gym gives up after 3 tries and those rollouts fail instead.)
Status
Open, not fixed in this PR. Raised as C21 (Gym sends the call to another frontend) and C22 (RL restarts a dead frontend and stops the run if it keeps dying), in a review that is still pending.
Background. A Dynamo frontend takes Gym's chat calls and passes each one to any of the vLLM engines. With num_frontends: 3, Gym gets 3 URLs and keeps each session on one of them. The engines run on GPUs and hold the calls; a frontend holds nothing the run needs to keep. Dotted words have a short explanation: hover or tap them.

Gym picks a URL per session by hashing the session id (_resolve_client). When that URL refuses the connection, Gym's HTTP client waits 0.5 s and tries the same URL again (http_client.py L818). It has no limit, because RL sets neither of the two options that would add one (app.py L1166-L1170); Gym's own comment says "a client retries a refused connection forever" (L714-L717). On the RL side, the driver reads the frontends' exit codes only while it waits for them at startup (L669, _assert_services_alive), and nothing restarts a frontend.

One frontend dies: this PR, and the proposed fix

When F1 diesWhat happens
The 4 enginesKeep running. The calls F1 had in flight are lost, since their replies have nowhere to go.
Gym's sessions on F1 (s2, s5)Retry F1's URL every 0.5 s, with no limit. With forest training (source_history), Gym tries only 3 times (openai_client.py L485-L486), so those rollouts fail instead of hanging. Either way, nobody tries F0 or F2.
The other frontendsKeep serving their own sessions, and could reach all 4 engines for s2 and s5 too. Nobody sends those calls to them.
The v2 driverDoes not notice. It checks the frontends only at startup, and nothing restarts one.
A checkpoint cutGym sends the cut for s2 and s5 to F1 (_cut_all). It fails, so those calls are generated again after a restore (_cut). That loses work but never gives wrong tokens.

Is the native vLLM path the same?

Gym's side is the same: the same client retries a dead URL forever. What differs is what can die.

Native vLLMDynamo (this PR)
What a Gym URL points atAn HTTP server thread inside one GPU worker (_setup_vllm_server)A frontend: its own CPU process, started by a FrontendHost actor
Can it die while the engines live?In practice no: it dies with its GPU worker, so the run has lost an engine anywayYes: the frontend can crash or run out of memory while every engine is fine
Can another URL take the call?Not without that engineYes: every frontend reaches every engine
Restart costA GPU worker and its weightsOne CPU process; it has no state the run needs

So the hang is not new in this PR, and #4979 had it with one frontend. What this PR changes is that the fix is now cheap: there are other frontends to fall back on, and a frontend is easy to restart.

The fix, as pseudocode (proposed, not implemented)

Where the fix lands: Gym and RL. C21: Gym's vllm_model resends a refused call to another URL, behind a config flag; RL turns the flag on for Dynamo. C22: RL only, in FrontendHost and the driver.

C21 · a Gym call, before

# Gym vllm_model · serving event loop, one task per call
def chat(session, call):
    url = pinned[session] or urls[hash(session) % 3]  # _resolve_client
    ticket.backend = url                              # note_generation_backend
    while True:                                       # max_connection_retries=None
        try: return await post(url, call)
        except ConnectionRefused: await sleep(0.5)    # same url, no limit

C21 · a Gym call, after

# Gym vllm_model · serving event loop, one task per call
def chat(session, call):
    url = pinned[session] or urls[hash(session) % 3]
    for url in [url] + other_urls(url):             # every frontend reaches every engine
        ticket.backend = url                        # the cut follows the call
        try: return await post(url, call)           # a few retries per url
        except ConnectionRefused: mark_failed(url)  # never sent, so safe to resend
    raise AllFrontendsDown                          # a clear error, not a hang

A refused connection means the call was never sent (is_unsent_connection_failure), so sending it elsewhere is safe in every Gym mode, forest training included. Real code: _resolve_client, the retry loop, note_generation_backend.

C22 · a frontend, before

# FrontendHost actor · one per frontend, 0 CPU, pinned to its node
def start(cmd):
    port = free_port()
    proc = launch(cmd, port)  # _ServiceProcess
    return url(port)          # handed to Gym once
# v2 driver
def wait_for_engines():       # startup only
    _assert_services_alive()  # the only read of a frontend's exit code

C22 · a frontend, after

# FrontendHost actor · one per frontend, 0 CPU, pinned to its node
def start(cmd):
    port = free_port()
    proc = launch(cmd, port)
    start_thread(watch, cmd, port)                   # new watcher thread in the actor
    return url(port)
def watch(cmd, port):                                # watcher thread
    while True:
        code = proc.wait()
        log(url(port), code)
        if restarts_in(10 min) >= 5: failed = code; return
        proc = launch(cmd, port)                     # same port, same chat files
# v2 driver, before each rollout
for host in frontends:
    if host.failed(): raise RuntimeError(url, code)  # an error, not a hang

Real code: FrontendHost.start, _start_frontends, wait_for_engines.

The two fixes help each other. While F1 restarts, C21 sends its calls elsewhere. Once F1 is back on the same URL, Gym's sessions can use it again. If F1 keeps dying, C22 stops the run with an error that names F1, instead of a silent hang.

So what. Today, one frontend crash stops training without an error, even though the GPUs and the other frontends are fine. With several frontends, that is avoidable. Ask Gym to send a refused call to another frontend (C21), and ask RL to restart a dead frontend on the same port, failing loudly when restarts run out (C22).
