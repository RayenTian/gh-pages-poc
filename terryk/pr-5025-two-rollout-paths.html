Background. A rollout is one prompt sent to the inference engine to get a completion back, with the log-probability of each new token. Dynamo's frontend can split one request across two engines: a prefill engine reads the prompt and builds its KV cache, then hands that cache to a decode engine over NIXL, which writes the answer. PRs 1–4 of this stack built those engines. Dotted words have a short explanation: hover or tap them.

Two paths to one Megatron rollout

Both paths start from the same call, generate_async, made by the trainer's rollout loop for one prompt. The direct path makes a Ray call to one Megatron worker, which runs prefill and decode in one engine. The new path builds an OpenAI completion request in generate_through_frontend and posts it over HTTP. The two meet again in the rollout loop, which reads only the new tokens and their log-probabilities. The example below is the PR's own unit test: prompt [1, 2, 3] padded to 4, one new token 8 with log-probability -0.5.

max_tokens:2 is the configured 16 cut to what fits: the test's max_model_len is 5 and the prompt is 3 tokens (allowed_new_tokens). top_k:-1 and top_k=0 both mean "off" in their own API.

Rollout call, after

# driver, rollout event loop; one call per prompt, many run at once
async def generate_async(data):
    raise NotImplementedError("do not serve rollouts yet")
    if data is empty: return
    url = dp_openai_server_base_urls[0]                  # the frontend's /v1 URL
    out = await generate_through_frontend(cfg, url, data)
    out["gen_leader_worker_idx"] = [0]                    # same as the direct path
    yield 0, out

# generate_through_frontend, same event loop
body = completion_payload(prompt ids, max_tokens = min(16, 5 - 3))
for attempt in 1..3:                                    # post_completion
    resp = await POST url + "/completions"               # new aiohttp session each try
    if not is_retryable(resp): break                # C12: own status list; timeouts retried
    sleep 1 s
ids, lps, truncated = parse(resp)                      # nvext.completion_token_ids, token_logprobs
return single_sample_output(...)

Where they meet, and what still differs

The trainer only reads output_ids and logprobs between the prompt length and unpadded_sequence_lengths, so the narrower output width on the Dynamo path changes nothing. These do differ after the two paths meet:

WhatDirectThrough Dynamo
truncatednot setset from finish_reason == "length" (noted in the author's own review)
ignore_eos: truehonoured with termination_id=-1dropped from the request (open thread)
a failed requesta Ray errorretried up to 3 times, timeouts too, using its own list of retryable statuses (C12)
CIrun in L1functional test written, not in any lane (C8)
So what. The new path gives the trainer the same tokens and log-probabilities as the direct one, so a reviewer can judge it as "the same rollout, over HTTP".
