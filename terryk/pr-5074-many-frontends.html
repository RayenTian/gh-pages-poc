Two pages on this PR, one question each. This one: what runs where, and how turn 2 of a rollout finds turn 1.

Background. A frontend is the HTTP side of a vLLM worker. The engine core runs the model and keeps the KV prefix cache. Turn 2 of a rollout starts with turn 1's tokens, so it runs fastest on the engine that already holds them. With token capture on, turn 2 also needs turn 1's exact token ids, which it reads from TQ. Dotted words have a short explanation: hover or tap them.

Each column follows turn 2 of one rollout through seven steps: ① receive the call, ② apply the chat template, ③ read turn 1's tokens from TQ and put them in front, ④ pick an engine, ⑤ turn images into pixels, ⑥ run the model and write the call to TQ, ⑦ reply. In native vLLM, Gym does ④ itself: it hashes the rollout id to pick one worker URL (_resolve_client). #5074 keeps that, then lets the OS pick a frontend inside the worker per connection (create_engine). In Dynamo, Gym can hit any frontend, and the KV router does ④ per call.

Picking where turn 2 runs: before (K = 1)

# Gym, per call
url = workers[hash(rollout_id) % N]    # same worker every turn
# vLLM worker = Ray actor, at startup
sock = reserve_port(range)             # listening socket, held open

thread: serve(app, sockets=[sock])     # uvicorn on its own thread

After (K = 3)

# Gym, per call (unchanged)
url = workers[hash(rollout_id) % N]             # same worker every turn
# vLLM worker = Ray actor, at startup
sock = reserve_port(range)
llm = AsyncLLM.from_engine_args(args)
pool = MultiAPIServerPool(self, K=3)
llm = pool.create_engine(args)                  # 1 engine core, 3 client slots
  for i in 1, 2:
    spawn run_api_process(i, sock)              # child: own AsyncLLM(client_index=i)
  llm = AsyncLLM(client_index=0)                # frontend 0 stays in the actor
thread: serve(app, sockets=[sock])              # frontend 0
pool.command("start")                           # children serve on the SAME sock
# kernel, per new TCP connection
give it to one of the 3 waiting accept() calls  # no session id; any frontend

Real code: _resolve_client (Gym), _reserve_port, create_engine, run_api_process, _setup_vllm_server.

    hit = longest cached prefix of keys

So what. Session stickiness still works, at the level that matters. Gym still pins a rollout to one worker. Inside the worker, turns spread across the K frontends. That is fine, because the KV cache sits in the one shared engine and turn 1's ids sit in TQ. The cost is an extra TQ read when turn 2 lands on a different frontend, and no generation-prefix cuts when K > 1. Dynamo gets the same result in a different way: its router chooses the engine by what is cached, call by call. The open risk is not routing: a failed metrics query can shut down the shared engine for all K frontends (next page).
