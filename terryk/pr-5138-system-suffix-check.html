Reusing saved tokens after an added system message: only when the prompt's start did not move

NVIDIA-NeMo/RL #5138 · depends on Gym #5771 · permalinks pinned to head 439d37b0

Before
When an agent added a system message after the model's answer (Claude Code does this for token-budget updates), Gym refused to link the call to the earlier one. Every such call started over as a new root, so its saved tokens were never reused.
This PR
Turns on Gym's allow_system_suffix for forest training on native vLLM, and adds an RL check: reuse the saved tokens only if the full prompt starts with the history exactly as rendered on its own. Otherwise, start a new root.
Status
The check is correct. The review found no case where it reuses tokens it should not. Not yet safe to merge: the Gym version RL pins rejects the new key (see page 2).

Two pages on this PR, one question each. This one: what the new check protects against. Dotted words have a short explanation: hover or tap them.

Background. In multi-turn training, RL keeps the saved tokens of each model call. On the next call, the vLLM chat server renders the whole chat with the template, then splices the saved tokens over the history part, so training sees exactly what the model saw. The splice finds the cut by counting end-of-turn tokens, not by position. A call that cannot be spliced safely becomes a new root.

Some chat templates move every system message to the top of the prompt. If a system message arrives after the answer, the template renders it before the history. Counting end-of-turn tokens then cuts in the wrong place: the system message is cut away and the history appears twice. The PR's fix is one comparison in _render_chat_call: does the full render start with the history render? Only decide_capture_input reads the answer, and only when the new messages include a system message.

The numbers are the ones the PR's own test uses, in test_system_suffix_checks_rendered_prefix_before_capture: lane A expects [10, 77, 31, 2, 99, 2, 7], and lane B expects the full render unchanged as a new root. The red box is the splice run by hand on lane B's tokens.

The change, as pseudocode

Render step, before (base 9a7640c)

# vLLM chat server, once per chat call (event loop); Dynamo's render pool runs the same method
def _render_chat_call(request, messages, admission):
    full = render(messages)
    if managed_capture:
        decision = resolve_capture_input(admission, messages)  # Gym never sent a system suffix
    if decision.serving.mode == "token_in":                       # only calls that will splice
        history = render(messages[:last_answer + 1])
    return full, history, decision

Render step, after

# same place, same thread
def _render_chat_call(request, messages, admission):
    full = render(messages)
    if admission.mode in ("candidate", "token_in"):            # moved up: now before the decision
        history = render(messages[:last_answer + 1])
    if managed_capture:
        stable = bool(history) and full[:len(history)] == history  # the new check
        decision = resolve_capture_input(admission, messages, stable)
    if decision.serving.mode == "token_in": history = render(...)
    return full, history, decision

What the review checked, and what it asks for

The check matches what Gym #5771 asks of the serving side (Gym doc). Gym admits a call when every new message is a user, tool or system message. RL runs the check whenever a system message is among them, in any order. If the first len(history) tokens are unchanged, a moved system message would have to sit after the history, so the splice cannot cut it away. A template that renders the last answer differently once something follows it (Qwen3 with empty reasoning adds an empty think block only when the answer is last) fails the check and starts a new root. That is safe, and no worse than before.

The asks are about landing, tests and docs, not the check:

  • C1: land with the Gym bump. At the current pin an existing unit test fails, and forest runs on vLLM fail at Gym startup (page 2).
  • C2: add a test that checks when allow_system_suffix is set.
  • C3: fix the guide's last sentence. Users cannot "leave the gate disabled"; RL sets it.
So what. With this PR, Claude Code's budget updates can keep reusing saved tokens whenever the template leaves the start of the prompt alone. When the template moves the system message, the call starts a new root instead of training on a prompt that lost the message. The one blocker is merge order: Gym bump first.
