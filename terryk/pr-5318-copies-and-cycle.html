Why finished rollouts got cheaper: no group copies to read an ID, and no closure loop holding results

PR #5318 · links pinned to head af39398 (before-code at base bf50129)

Before
Each finished sibling made a full deep copy of its prompt group just to read one ID. Finished results also stayed in memory until Python's cyclic garbage collector ran.
This PR
Adds two small ledger reads that return just the strings, and cuts the function loop in the stream code once all streams end.
Status
Fixed by this PR when the streams finish normally. Open: on the group deadline or a failed stream, finished results still wait for the collector (review comment C1, below).
Background. The rollout manager keeps a recovery ledger. Each record has one entry per sibling. When a sibling finishes, its entry is sealed: it gets a receipt. get_group() returns a deep copy of the record, so callers cannot change the ledger by mistake. Dotted words have a short note: hover or tap them.
Why it should be faster.

The old code deep-copied the whole sibling list, receipts included, to read one string. Sibling k copied k sealed receipts, so a group of 16 copied 0+1+…+15 = 120 receipts for ID checks alone, plus 2 full copies at finalize. The new reads touch only the strings. The one receipt copy per sibling that the finalize request needs stays.

The loop fix does not save compute. It lets finished results be freed as soon as the streams end, instead of piling up until the garbage collector runs, which costs time at high concurrency.

1 · Reading an ID no longer copies the group

Example: one prompt group with 4 siblings. _record_streamed_completion runs once as each sibling finishes and checks that the stream's rollout ID matches the ledger's. When the last one seals, it builds the finalize request and reads the agent name and attribution key.

Before

# rollout pump, one event loop. Runs once per finished sibling.
async def _record_streamed_completion(group, i, gate_id):
    rec = ledger.get_group(group)                        # deep-copies every sibling and receipt
    if gate_id != rec.gate_rollout_id(i): raise          # ...to read one string
    ...
    # last sibling sealed: build the finalize request
    inputs = ledger.finalization_inputs(group)           # copies each receipt once, on purpose
    agent = ledger.get_group(group).resolved_agent_name  # full copy again
    key   = ledger.get_group(group).attribution_key      # and again

After

# rollout pump, one event loop. Same callers, same order.
async def _record_streamed_completion(group, i, gate_id):
    rec = ledger.get_group(group)
    if gate_id != ledger.current_gate_rollout_id(group, i): raise  # one string, no copy
    ...
    inputs = ledger.finalization_inputs(group)                     # unchanged
    agent = ledger.get_group(group).resolved_agent_name
    key   = ledger.get_group(group).attribution_key
    agent, key = ledger.finalization_routing(group)                # two strings, no copy

Real code: current_gate_rollout_id, finalization_routing, call sites L3170 and L3283. Test: test_streamed_identity_and_routing_do_not_copy_sealed_receipts makes _copy_group fail if it sees a sealed receipt.

2 · Finished results are freed when the streams end

_stream_rows runs each Gym stream as its own task. If Gym refuses a row, consume() calls submit() to re-send it, and submit() starts a new consume(). Two inner functions that point at each other form a loop, and Python's normal reference counting cannot free a loop. Everything they share (the results list with its receipts, the completion callback) waited for the cyclic garbage collector.

Before

# _stream_rows: one event loop; each consume() is its own asyncio task
async def consume(rows):
    async for item in gym_stream(rows):
        if item is a refused row: submit([row])  # consume -> submit
        results[idx] = item; await on_completion(idx, item)
def submit(rows):
    streams.add(create_task(consume(rows)))      # submit -> consume: a cycle
submit(pending)
try:     wait until every task in streams ends
finally: cancel the rest; gather(*streams)
return                                           # results and on_completion wait for cyclic GC

After

# _stream_rows: same tasks, same cancel-and-wait on exit
async def consume(rows):                        # unchanged, still calls submit
consume_stream = consume                        # the only path from submit to consume
def submit(rows):
    streams.add(create_task(consume_stream(rows)))
submit(pending)
try:     wait until every task in streams ends
finally:
    try:     cancel the rest; gather(*streams)  # every task is done after this
    finally: consume_stream = None              # cuts the cycle
return                                          # plain refcounting frees results now

Real code: L1565–L1593. Test: test_stream_closures_release_completed_receipts_without_cyclic_gc turns the collector off and checks that a weak reference to the finished result is dead. It fails on the base commit and passes at head.

Still open (C1): the two error exits. The reset sits in a finally, but it only helps when every stream ends normally. On the group deadline or a failed stream, a second loop holds the results: the cancelled or failed task keeps its error, the error's traceback keeps the consume (or _stream_rows) frame, and that frame reaches streams and finished (or the local task), which still hold the task. Nothing leaks, but the results wait for the collector, the same late free the PR fixes for the normal path. With the collector off, a test that lets row 0 land and then hits the deadline (or makes the stream raise) finds row 0's result still alive at head.

The fix, as pseudocode (proposed, not in the PR; tested on a copy)

# _stream_rows, inner finally: runs on every exit
finally: consume_stream = None
         streams.clear(); drain finished  # the cancelled task is no longer held here
         task = None                      # nor by the frame a failed stream's traceback keeps

With both lines, a deadline test and a failed-stream test pass (both fail at head), and so does the PR's own weakref test.

So what. Copies that grew with the square of the group size are gone from the per-completion path, and finished results no longer pile up between garbage-collector runs. Correctness does not change: the new reads return the same values as the old copies. One gap is left: on the group deadline or a failed stream, results still wait for the collector. Two more lines in the same finally close it (C1).
