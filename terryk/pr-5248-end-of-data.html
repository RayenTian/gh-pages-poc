Three pages on this PR, one question each — this one: what happens when a step loses a group.

Background. Page 1 showed that every chunk must be a whole multiple m of groups. A step plans num_prompts_per_step groups, but two things can shrink it after setup:
  • C1 — dynamic sampling at end of data. With dynamic sampling, a group whose answers all score the same is thrown away and a spare prompt replaces it. Once the data runs out there is no spare, so the step is marked allowed to close short.
  • C5 — a dropped prompt. With a drop budget above 0 and on_dropped_prompt: shrink (the default), a prompt that keeps failing is given up and the step closes without it.
This is not the windowed sampler's end-of-data tail: the PR already stops cleanly there. Dotted words have a short explanation: hover or tap them.

Either way the step's target drops by one: 8 → 7. _target_groups_for_step returns 7 as is. The pump then asks the sampler for 7 groups in whole multiples of 2, and no such number exists, so _finalize_selection raises. The fix rounds the target down to a whole multiple, and the existing min_step_batch_fraction check decides what happens to the smaller step.

Target 8 → 7, in multiples of 2

The fix — proposed, not in the PR

Nothing below is implemented. It is the fix in review comment C5, which also covers C1.

Where the fix lands: RL only. One rounding line in _target_groups_for_step, a clearer floor error, and new wording for the setup warning and the docs.

The fix, as pseudocode (proposed; run on CPU)

# train pump, every time it needs the step's target
def target_groups_for_step(step):
    target = num_prompts_per_step - shortfall[step]
    kept = num_prompts_per_step - shortfall[step]      # 8 - 1 = 7
    target = kept - kept % m                          # 6: whole multiples of 2
    if step in steps_allowed_short:                   # C1: end of data
        return target                                 # trained or skipped later by the floor
    if target < floor:                                # C5: a dropped prompt
        raise RuntimeError("... leaving 7 (6 in whole multiples of 2) ...")
    return target

The same step in a bigger run: 18 prompts, multiple 3, one prompt dropped → at head No multiple of 3 fits selection bounds [17, 17]; with the fix it stops cleanly at fraction 0.9, and trains 15 at 0.8.

So what. On a GRPO run with m > 1, any step that comes up short by a non-multiple ends the run with a sampler error that names neither dynamic sampling nor drops. The shipped dapo-nanov3.5 single-controller recipes (multiple 2, in_order, dynamic sampling) hit it if a run reaches the end of its data.
