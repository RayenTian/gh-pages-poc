Where a captured request's logprobs go, with and without packing

NVIDIA-NeMo/RL #5266 (“perf(vllm): add opt-in packed captured logprob histories”). NeMo-RL links pin the PR head 8299d55f; vLLM links pin v0.33.0 (4ba787ec).

Before
With flat_logprobs: true, vLLM's own code stores each generated token's logprob. Per engine step it turns the numbers into Python lists, decodes each token to text, and appends to a FlatLogprobs object.
This PR
Adds packed_capture_logprobs (off by default). For captured, text-only, no-top-k, non-streamed requests, it swaps vLLM's store for three numeric arrays and a bulk append, and reads the selected values back without building a dict per token.
Status
Open — one crash bug, and no speed numbers on this head yet. The crash is on the next page; both are in the review comments.
packed vs native top-k crash

Two pages on this PR, one question each. This one: what the new path does differently.

Background. In RL training, each generated token needs the log-probability the generator gave it, so training can compare it to its own. NeMo-RL serves vLLM over HTTP. For captured requests it reads the logprobs straight from vLLM's per-request state with extract_generation_logprobs. The cost this PR attacks is CPU time on the generation actor while vLLM files those numbers away, one token at a time. Dotted words have a short explanation: hover or tap them.
Why it should be faster. The GPU work is the same in both paths. The packed path skips three CPU steps per token: turning numpy rows into Python lists, decoding the token to text (vLLM's convert_ids_list_to_tokens + _verify_tokens), and one append per token. A multi-token step becomes one frombytes copy per column. Nothing reads the skipped text for captured requests: NeMo-RL already skips building the reply's logprob objects for them (vllm_worker_async.py:2390). The only numbers so far are an older CPU-only synthetic run (8 requests × 131,072 tokens: 7.56 s → 6.07 s), not measured on this head and not as a share of a training step.

One token, through both paths

One engine step makes one token for one captured request: token 7, logprob -0.5, rank 4. vLLM hands it over as ids [1, 1] = [positions, columns]. Column 0 is always the sampled token. The hook decides per request which path the request takes (patches.py:72-80). Values below are from a real run of the PR's class.

The same change as pseudocode

Per engine step, before (native vLLM)

# generation actor, vLLM output loop (one task)
def _update_sample_logprobs(rows):
    for ids, vals, rank in rows:               # one loop turn per token
        ids, vals = ids.tolist(), vals.tolist() # numpy → Python lists
        text = decode(ids)                      # tokenizer, per token
        cumulative += vals[0]
        append_logprobs_for_next_position(store, ids, vals, text, rank)

Per engine step, after (packed request)

# generation actor, vLLM output loop (one task)
def update(rows):                              # set on this request only, at add_request
    before = len(history)
    history.append_arrays(ids, vals, ranks)  # whole step at once; C3: rows can be wider
    cumulative = history.cumulative_after(cumulative, start=before)
    for ids, vals, rank in rows: ... decode(ids) ...

Real code: PackedCaptureLogprobs, PackedSelectedLogprobs, installed from setup_token_capture on every HTTP frontend.

So what. Both paths hand training the same numbers, and for captured requests nothing reads the text the new path skips. So this is a pure CPU saving on the generation actor, if it holds up. Two things block it: a crash when another request in the same engine step asks for top-k logprobs (next page), and no numbers yet on this head that show the saving as a share of a training step.
