Background. Dynamo needs three services: etcd (where engines list themselves), NATS (events) and the frontend (HTTP). Each engine runs a Dynamo Worker wrapped around an adapter that knows how to talk to that engine. In prefill/decode serving, one engine reads the prompt (prefill) and hands its KV cache to a second engine that writes the answer (decode). Dotted words have a short explanation: hover or tap them.

Two ways an engine joins the frontend

vLLM already does this: once the engines load, the driver asks each data-parallel leader to start its endpoint, which wraps the engine in NeMo-RL's own adapter. A Megatron engine has no weights until the first refit, so this PR starts its endpoint in the first resume_after_refit. It also uses Megatron-LM's adapter, MegatronLLMEngine, which does not hold the engine. It waits for a "ready" message with the address of the engine's coordinator, then sends requests there. Example below: vLLM with 3 data-parallel leaders, and Megatron with 1 prefill engine (2 GPUs) and 1 decode engine (4 GPUs).

Inside ③ on the right, the second call in ② is attach_dynamo_events: rank 0 connects an event reporter to port 4000 and sends ready {coordinator_address}. Only after that does the adapter register the engine.

Where they become one. Both use the same ManagedDynamoRuntime.start for the services, the same wait_for_engine_registrations poll (this PR moves it out of the class so the controller's copy, which owns no service process, can run it over HTTP), and the same Dynamo Rust Worker. What still differs after that: the adapter class (NeMo-RL's vs. Megatron-LM's), when it starts (after load vs. at the first refit), how it reaches the engine (direct call vs. the coordinator), the component names, and how the plane and port settings are read.

Controller: the first resume after a refit, before

# driver or controller copy; one call per training step

After

# driver or controller copy; one call per training step
def resume_after_refit():
    errors = restore_engines()          # every engine resumes, bounded by a deadline
    if errors: raise
    if fleet_ready: return                    # only the first resume does the rest
    for engine in engines:                    # in order, one deadline for all
        meta = engine.rank0.start_dynamo_endpoint(…)  # {event_port: 4000, system_port: 4001}
        engine.all_ranks.attach_dynamo_events(meta.addr) # rank 0 sends "ready"
    wait({"prefill": 1, "backend": 1}, check_alive)
    fleet_ready = True

What the review asks

The shared parts hold up: the services are one class, the wait is one function both sides call (the controller's copy too), and the endpoint lifecycle has CPU tests. The main ask is the adapter in ③ (C1): build a NeMo-RL DynamoMegatronAdapter on main's DynamoEngineAdapter, as vLLM does, instead of hosting Megatron-LM's MegatronLLMEngine. The design and what the later PRs then do are on the one P/D interface page. The other three are small: the controller test's fake worker accepts any argument name (C2), after #4801, Megatron's config should not carry render_workers or session_affinity_ttl_secs (they do nothing until #5097 turns chat on), so each backend passes them to the runtime instead (C3), and two docstrings are stale (C4).
