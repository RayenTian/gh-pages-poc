Four pages on #4946 and the two PRs stacked after it — this one: what the third average adds and where it can run.

Before
Two averages: global_token_mean (every token counts the same, so long answers weigh more) and sequence_mean (every answer counts the same).
This PR
Adds a third, group_token_mean: take the token mean inside each prompt group, then give every group the same weight. Single-controller GRPO with Megatron only.
Status
Proposed — open, not merged. Off unless you set loss_fn.normalization: group_token_mean.

Background. GRPO answers each prompt several times (num_generations_per_prompt) and scores each answer against the others for the same prompt. Those answers form a prompt group. Page 1 shows the reducer object that picks the average; page 2 shows how the trainer divides once per step. This page adds a third reducer to that slot. Dotted words have a short explanation: hover or tap them.

CodeAll three go through the same reduce() call from #4946. The new GroupTokenMeanReduction is the token mean with each token scaled by its weight and the divisor swapped for the group count. The PR's GPU test checks exactly that against a token-mean run on scaled masks.

Where they split: the group divisor is neither a token count nor an answer count, so it has to be built up chunk by chunk. That is the third count and the StreamingObjectiveLoss wrapper that #4946 added and left unused. The one-call train() path never gets that count, so loss_divisor() raises there.

Where the weights come from

Where it lands: RL only. New code in interfaces.py (the weights and the reducer) and one call in the advantage step. The column is registered with the data store in single_controller.py. No worker change: the worker already does everything through the reducer.

Each row needs 1 / tokens in its group. Only the advantage step can make it: there, every chunk still holds whole prompt groups. Later the chunk is split across DP ranks and packed, and a group's answers can end up on different GPUs.

Advantage step, after (same example: chunk 1 = group P, chunk 2 = group Q)

# advantage step: controller process, once per chunk (whole prompt groups, before the DP split)
adv = grpo_advantages(rewards, prompt_ids)                           # unchanged
w = R.prepare_batch(sample_ids, token_mask, sample_mask,             # {} for the other two averages
                    group_indices=prompt_ids,
                    expected_group_size=num_generations_per_prompt)  # a partial group is an error
#   inside group_token_mean_weights:
    lengths = token_mask[:, 1:].sum(-1) * sample_mask                # A 4, B 1 | C 6, D 3
    totals  = scatter_add(lengths, by group)                         # P 5 | Q 9
    w       = 1 / totals[group of row]                               # A .2, B .2 | C .111, D .111 (0 if empty)
tq.put(rows, advantages, + w)                                        # new column: group_token_mean_inverse_tokens

Megatron worker: the hooks #4946 added, now in use

# Megatron worker, train_microbatch: once per chunk, every DP rank (no new worker code)
c = R.local_counts(chunk)                   # sum(len·w): P 4×.2 + 1×.2 = 1;  Q 6/9 + 3/9 = 1
loss_fn = StreamingObjectiveLoss(loss_fn)   # only for this reducer
actor = R.reduce(v, w, d=1)  →  sum(v · w)  # P 2.1 × .2 = .42;  Q 5.1 / 9 = .567
# finish_train_step: once per optimizer step
objective = all_reduce_over_DP(c)           # 1 + 1 = 2 groups
n = R.loss_divisor(toks, seqs, objective)   # returns objective = 2
grads *= 1 / n                              # loss (.42 + .567) / 2 = .493

Real code: group_token_mean_weights, GroupTokenMeanReduction, _train_microbatch_body, _finish_train_step_body.

Where you can use it

CaseWhat happens
TrainerSingle-controller GRPO, Megatron, no on-policy distillation. Anything else (PPO, the older GRPO loop, the DTensor backend) fails at setup; on the single-controller path the check runs before the cluster starts.
Loss optionsRejected: GSPO-style sequence-level ratios, OPD-full, positive-example NLL, and in-loss sequence filtering. Each would change masks or add a term that does not share the group weights.
MoE router losses, attached MTP headsRejected by the same check as sequence_mean: their gradients need the token count, and the group count is not it.
A group missing answersError: every group must have exactly num_generations_per_prompt rows, or its total would be wrong.
Groups where every answer got the same rewardStill count as one group in the divisor, even though their advantage is 0 and they add no gradient. Tokens that importance-weight rejection drops also stay in the count.
So what. group_token_mean gives each prompt an equal say, as sequence_mean gives each answer, but inside a prompt it still weighs every token the same. Use it when some prompts get much longer answers than others and you don't want those prompts to dominate the step. It is opt-in. The PR's 300-step comparison runs are in this review thread.
