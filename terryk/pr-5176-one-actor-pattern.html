Which CPU data-plane actors should share code? The two the controller owns, not the prefix writer

NVIDIA-NeMo/RL #5176, part 11 of 11 in the partial-checkpointing stack. A design proposal from the review, not part of the PR. "Before" links pin 981376a; "after" links pin the draft's a73b857.

Before
Two CPU Ray actors on main, AdvantageActor and RolloutReassemblerActor, each build a TQ client and repeat the same start-up, cleanup and checkpoint hooks.
This PR
Adds a third, PrefixWriterActor. It looks similar but differs in owner, count, placement and how data reaches it.
Status
Proposed, as draft PR #5256, not blocking #5176. The two controller-owned actors share one small base and one start helper; the prefix writer stays as it is.

Four pages on this PR. This one: which of the three CPU data-plane actors should share code, before and after.

Background. All three actors exist because some work on TQ is too slow, or too big, to do in the process that needs it, so it moves to a CPU-only Ray actor with its own TQ client. A shared base is worth it only where the base does most of the work and each actor adds a little; where the actors differ in what matters, a base just gets in the way. Dotted words have a short explanation: hover or tap them.

Same in the left column, different in the right: so the first two share a base, and the writer stays its own class. An earlier version of this page put all three behind one base and one pool; on real code that added a process() rename nobody called generically, a pool of one for the writer, and +128 lines.

Measured on the draft. Thirteen of the new lines are the license header; the rest roughly breaks even with what the two actors drop.

So what. Sharing pays for the two actors the controller owns: they are the same thing with a different job, so the base does the plumbing and each keeps only its job and its placement. The prefix writer only looks similar; forcing it in added a rename, a pool of one and more lines than it removed. #5256 changes nothing in #5176's own code, so it is an FYI for this review, not a request.
