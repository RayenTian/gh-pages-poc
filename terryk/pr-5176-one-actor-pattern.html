Four pages on this PR. This one: whether the new writer and two existing CPU actors can share one offload client and pool.

Background. All three actors exist for the same reason: some work on TQ is too slow, or too big, to do in the process that needs it, so it moves to a CPU-only Ray actor with its own TQ client. They differ in only three ways: how many there are, where they run, and how their input arrives. Two read their input from TQ themselves and get only metadata over Ray; the prefix writer gets its rows over Ray. Dotted words have a short explanation: hover or tap them.

Three copies of one pattern, and the shared version

QuestionAnswer, from the code
Two ways to get data?No second read method needed. A request is either metadata, and the actor reads TQ itself (advantage, reassembler; both already enforce it with assert_metadata_only), or byte columns sent through Ray (prefix writer), which the writer turns back into a TensorDict with C2's from_bytes. Neither needs anything from the base.
One caller, many actors?asyncio.gather over one call per shard; each call takes a free actor with acquire and gives it back with release. How to split the work stays with the caller: split_meta_by_prompt_group knows prompt groups and which estimators allow a split; generic code cannot.
One method to override, or read / compute / write?One: process(request). Splitting it into read, compute and write hooks fits only the advantage stage: the writer has nothing to read or compute, and the reassembler reads staging rows, writes finalized rows and clears staging in an order it controls. Extra methods (the writer's clear_samples, the reassembler's check_dependencies) stay plain methods, called on an actor from pool.acquire().
Why does a client need checkpoint and metrics hooks?On the Mooncake TQ backend each client process lends the store memory (64 GiB by default), and the rows it writes live there. A TQ checkpoint therefore asks every such process to save its rows: the controller lists the advantage actors and finalizers for exactly that (L455-L464). A client built with segment_size=0 holds no rows and needs no hook; the prefix writer already does this. So the base holds no rows unless a subclass sets owns_storage. get_data_plane_snapshot returns only I/O counters (bytes, wall time per op), which the controller sums across processes; get_data_plane_metrics says that.
Why these names?"Data-plane actor" sounds like the TQ storage actors that hold the data. "Detached" already means something in Ray: lifetime="detached" is an actor that outlives the process that made it, and these die with their owner. OffloadClient says what it is: a TQ client the caller hands work to. OffloadPool.start is a class method, so there is one entry point.
Telling actors apart in logs?__repr__ on the actor class sets Ray's log prefix (Ray docs), so 4 writers on one node print as PrefixWriter[0] … PrefixWriter[3].
Placement and failure?place covers today's three: pinned to the caller's node (writer), spread off the head node (advantage), default plus its own Python env (reassembler). All three already use max_restarts=0, and the controller already drops an advantage actor whose call failed (L5129-L5143); the pool does the same for every user.

Same shape: a CPU actor with its own TQ client, a start function, a caller that tracks which actor is free. Different: how many, where, and whether rows come through Ray or are read from TQ.

Proposed: one shared interface

# new: nemo_rl/data_plane/offload.py (proposed, ≈ 90 lines)
class OffloadClient:                                                                      # a CPU process with its own TQ client, doing one job
    owns_storage = False                                                                  # True: rows it writes live in its own memory (Mooncake)
    def __init__(self, dp_config, *, label):
        self.dp = build_data_plane_client(dp_config, bootstrap=False,
                                          segment_size=None if self.owns_storage else 0)  # 0 = holds no rows
        self.label = label
    def process(self, request):                                                           # the one method a subclass overrides
        raise NotImplementedError                                                         # read, compute, write: its choice
    def __repr__(self): return f'{type(self).__name__}[{self.label}]'                     # Ray prints this in front of each log line
    def get_data_plane_metrics(self): ...                                                 # today get_data_plane_snapshot: I/O counters, no data
    def mooncake_checkpoint(self, body): ...                                              # only used if owns_storage: save the rows it holds

class OffloadPool:                                                                        # one per user; never shared
    @classmethod
    def start(cls, client_cls, *args, n, placement=None, **ray_opts):
        actors = [ray.remote(client_cls).options(num_cpus=1, max_restarts=0,              # the options all three use today
                  scheduling_strategy=placement(i), **ray_opts).remote(*args, label=i) for i in range(n)]
        return cls(actors)                                                                # does not wait
    def wait_ready(self, method='__ray_ready__', *, timeout_s=None)                       # kill all if one fails
    async def wait_ready_async(self, method, *, timeout_s=None)                           # for a caller with a serving loop
    async def acquire(self)                                                               # wait until an actor is free, take it
    def release(self, actor)                                                              # give it back; never after a failed call
    size; free; def kill(self)                                                            # free = idle actors (finalizer queue metric); kill at shutdown

How each user calls it. The controller takes a free actor with acquire, calls process, and releases it unless the call failed (advantage shards and finalizers alike). The prefix writer is a pool of one, so it calls pool.actors[0].process directly; Ray runs its calls in order.

Real code it replaces: advantage_actor.py, RolloutReassemblerActor and its start function, PrefixWriterService … create_prefix_writer, and the same two hooks in TQWorkerMixin.

One pool per use, never shared. Each OffloadPool.start call returns its own pool with its own count and placement: 4 vLLM engines on a node make 4 pools of 1 writer, each pinned to that node; the controller makes one pool of N advantage actors placed anywhere off the head node, and one pool of K finalizers. What is shared is the code, not the actors.

The one real difference: the controller takes the checkpoint lock only after an actor is free, so the lock never covers time spent waiting in an actor's queue. acquire() keeps that: the pool hands out an actor only when it is idle.

Measured on the draft, not estimated. An earlier estimate here said ≈ −110; it assumed C2's removal of RayPrefixWriterClient (94 lines), which the draft leaves alone, and a shorter base. The payoff is per new actor: the next one is a subclass with one method instead of another ≈ 100 lines of plumbing.

So what. The three actors reconcile into one client base class with one method to override, and one pool class that each user starts its own copy of, and nothing more. No second read method, no read/compute/write hooks, no sharding logic in the base. Today it adds lines rather than removing them, but a fourth actor becomes a short subclass, and the prefix writer gets the checkpoint hooks it lacks today. The draft is #5256; it is not blocking #5176.
