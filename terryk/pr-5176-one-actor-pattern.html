Four pages on this PR. This one: whether the new writer actor and two existing CPU actors can share one small base.

Background. All three actors exist for the same reason: some work on TQ is too slow, or too big, to do in the process that needs it, so it moves to a CPU-only Ray actor with its own TQ client. They differ in only three ways: how many there are, where they run, and how their input arrives. Two read their input from TQ themselves and get only metadata over Ray; the prefix writer gets its rows over Ray. Dotted words have a short explanation: hover or tap them.

Three copies of one pattern, and the shared version

QuestionAnswer, from the code
Two ways to get data?No second read method needed. A request is either metadata, and the actor reads TQ itself (advantage, reassembler; both already enforce it with assert_metadata_only), or byte columns sent through Ray (prefix writer), which the base turns back into a TensorDict with from_bytes.
One caller, many actors?pool.map sends one request to each actor in parallel. How to split the work stays with the caller: split_meta_by_prompt_group knows prompt groups and which estimators allow a split; generic code cannot.
Running a computation?Each subclass's own method is the computation (run, finalize, put_samples). A single __call__ does not fit: the writer needs two methods (put and clear), and the reassembler also has check_dependencies.
Telling actors apart in logs?__repr__ on the actor class sets Ray's log prefix (Ray docs), so 4 writers on one node print as PrefixWriter[0] … PrefixWriter[3].
Placement and failure?place covers today's three: pinned to the caller's node (writer), spread off the head node (advantage), default plus its own Python env (reassembler). All three already use max_restarts=0, and the controller already drops an advantage actor whose call failed (L5129-L5143); the pool does the same for every user.

# new: nemo_rl/data_plane/actors.py (proposed, ≈ 110 lines)
class DataPlaneActor:                                                         # a CPU Ray actor that owns a TQ client
    def __init__(self, dp_config, *, label, **client_opts):
        self.dp = build_data_plane_client(dp_config, bootstrap=False, **client_opts)
        self.label = label
    def __repr__(self): return f'{type(self).__name__}[{self.label}]'         # Ray prints this in front of each log line
    def mooncake_checkpoint(self, body): return run_checkpoint_command(body)  # today copied in 3 classes
    def get_data_plane_snapshot(self): ...                                    # today copied in 3 classes
    def from_bytes(self, columns) -> TensorDict: ...                          # rows sent through Ray, read in place

def to_bytes(fields: TensorDict) -> columns: ...                              # caller side; NumPy views, no copy (C2)

def start_data_plane_actors(cls, *args, n, place, **ray_opts) -> DataPlaneActorPool:
    actors = [ray.remote(cls).options(num_cpus=1, max_restarts=0,             # the options all three use today
              scheduling_strategy=place(i), **ray_opts).remote(*args, label=i) for i in range(n)]
    ray.get([a.__ray_ready__.remote() for a in actors])                       # on failure: kill all, raise
    return DataPlaneActorPool(actors)

class DataPlaneActorPool:                                                     # an asyncio.Queue of free actors
    async def call(self, method, request)                                     # any free actor; a failed call drops that actor
    async def map(self, method, requests)                                     # one request per actor, in parallel
    def send(self, method, *args) -> Future                                   # don't wait: actor.method.remote(...).future()

Real code it replaces: advantage_actor.py, RolloutReassemblerActor and its start function, PrefixWriterService … create_prefix_writer, and the same two hooks in TQWorkerMixin.

So what. The three actors reconcile into one base class, one start function and one pool, about 110 lines, and nothing more: no generic __call__, no second read method, no sharding logic in the base. The line count drops only a little, but a fourth actor becomes a ten-line subclass, and the prefix writer gets the checkpoint hooks it lacks today. To keep #5176 from growing, the base lands first in its own small PR.
