Two pages on this PR, one question each — this one: what the new class does next to the old one. The stack's first PR has its own page: where the Dynamo switch sits.

Background. A prefill/decode split runs prompt reading and answer writing on different engines; Dynamo's frontend routes each request across them. A refit pushes new weights from the trainer into every engine after each step. Dotted words have a short explanation: hover or tap them.

The new class, MegatronDynamoGeneration, is not a subclass of MegatronGeneration. It holds several of them. megatron_generation_cls picks it when dynamo: true. The example below uses 16 trainer ranks and one inference node of 8 GPUs, split as 1 prefill engine at TP 4 and 2 decode engines at TP 2.

One policy vs. one policy per engine

Where they meet: each Dynamo engine is a plain MegatronGeneration built from a copied config, so the worker code is the same. They split in exactly three hooks on the worker — extra config fields, which engine class to build, and where the coordinator listens. The plain worker returns the old answers; MegatronDynamoGenerationMixin returns the Dynamo ones.

This PR: one call per engine

# driver / controller, one call each, in engine order
def init_collective(ip, port, world_size=24, train_world_size=16):
    offsets = engine_rank_offsets(16)             # [16, 20, 22] from widths (4, 2, 2)
    for engine, off in zip(engines, offsets):
        engine.workers.init_collective(..., rank_offset=off)  # prefill-0: 16..19, decode-0: 20..21, decode-1: 22..23
So what. The design is clean: the plain Megatron path gains three small hooks and no Dynamo branches, and every Dynamo-only piece lives in its own class and mixin. But nothing in this PR has run on a GPU, and the engine build cannot pass at the repo's Megatron-LM pin. That fix belongs in this PR, because no later PR in the stack moves the pin.
