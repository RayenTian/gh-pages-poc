Setup now waits for the slowest of three steps, not their sum

NVIDIA-NeMo/RL #5154 · perf(single-controller): overlap refit init with actor pools · permalinks pin head 6dac75f (base 047d885)

Before
At the end of single-controller setup, three unrelated steps ran one after another: connect the trainer to the inference engines for weight updates, start the rollout reassembler actors, start the advantage actors. Setup paid the sum, ~40 s.
This PR
Runs the three at the same time and waits for the slowest. With non-colocated vLLM and no OPD teachers, the weight-update connection starts even earlier, as soon as the trainer and the inference engines are built.
Status
Works as described; safe to land after small fixes. The review found no bug. It asks for two test fixes and an update to the PR description (3 comments, none blocking).

Why it should be faster. The three steps share no state, and none of them is busy on the driver. One waits on a network handshake between GPUs, the other two wait for Ray to start CPU actors. So they can wait at the same time. Nothing gets cheaper: each step takes as long as before (16.1 / 10.5 / 13.2 s in the author's run, then 15.3 / 10.3 / 11.0 s).

Measured (author's multi-node async GRPO run, vLLM + NeMo-Gym): time on these steps 40.1 s and 38.0 s (two runs before) → 15.7 s, so 22–25 s saved. Total setup 341 / 344 s → 315 s. Most it can save: the two shortest steps; the longest one (usually the weight-update connection) is still paid in full, unless the early start hides it behind other work. Never slower except for three short-lived threads. That run seems to predate the early start (its timing line still lists the connection as a tail step), so the early start itself is not measured yet.

The weight-update connection is the refit communicator: the trainer GPUs and the vLLM GPUs join one NCCL group, so later steps can copy new weights into vLLM (_init_communicator). The two actor pools (_create_finalizers, _create_advantage) only need the data plane. The PR submits all three to one thread pool and joins them before the rollout manager is built (L2527-L2538), so both pools still exist before any checkpoint restore.

Before and after, on the author's numbers

The code, as pseudocode

Before · driver main thread

# setup_single_controller, driver main thread
trainer, generation = build_in_parallel()
finish_gym(); restore_data_plane(); setup_token_capture()
sync = init_communicator(trainer, generation)  # 16 s, NCCL handshake
finalizers = create_reassemblers()            # 10 s, Ray actor start
advantage = create_advantage_actors()         # 13 s, Ray actor start
build_rollout_manager(sync, finalizers, advantage)

After

# setup_single_controller, driver main thread
check_router_replay_config()                  # moved: now fails before any build
trainer, generation = build_in_parallel()
comm = None
if early(vllm and not colocated and not teachers):
    comm = start_on_daemon_thread(init_communicator)  # runs beside the next line
finish_gym(); restore_data_plane(); setup_token_capture()  # driver-side or async vLLM calls
with ThreadPool(3) as tail:                        # tail pool, one thread per step
    fin = tail.submit(create_reassemblers)
    adv = tail.submit(create_advantage_actors)
    comm = comm or tail.submit(init_communicator)
sync, finalizers, advantage = comm.result(), fin.result(), adv.result()  # fixed order
sync = init_communicator(); finalizers = ...; advantage = ...
build_rollout_manager(sync, finalizers, advantage)

Real code: _init_communicator, _start_on_daemon_thread, tail join.

Why the early start is safe. While the connection is being set up, the main thread calls the same workers. The data-plane restore runs on the driver (load_data_plane_checkpoint), and the vLLM calls (setup_token_capture, set_rollout_weight_version) are async and run no NCCL work on the engine. So at worst a call waits; it cannot deadlock. OPD teachers are left out because loading the teacher's output layer runs NCCL work on the trainer workers, which must not mix with the connection setup.
