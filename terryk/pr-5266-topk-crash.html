A request that asks for top-k logprobs crashes packed capture for its whole frontend

NVIDIA-NeMo/RL #5266. NeMo-RL links pin the PR head 8299d55f; vLLM links pin v0.33.0 (4ba787ec).

Before
vLLM's own code stores a no-top-k request's logprob fine, even when a neighbor in the same engine step asked for top-k: it keeps only the first column.
This PR
The packed store accepts only one column per row and raises on anything wider, inside vLLM's output loop.
Status
Open — not fixed in this PR. Raised in review comment C3 with a 1-line fix. Found by reading vLLM 0.33 source plus a CPU run of the PR's class; not run on a GPU.
packed vs native top-k crash

Two pages on this PR, one question each. This one: the crash and its fix.

vLLM samples all running requests together in one engine step. If any request in that step wants top-k logprobs, vLLM makes the logprob array that wide for every row: max_num_logprobs + 1 columns (gpu_input_batch.py:1139, outputs.py:34). Each request then gets its own rows, but the columns are not cut (slice_request). Column 0 is always the token that was sampled. The packed hook itself sends captured top-k requests down the native path (patches.py:76), so they are expected to share the engine.

One engine step, two requests

The values come from a CPU run of the PR's PackedSelectedLogprobs, fed one 1-column row (-0.5) and then the 3-column row above. Native vLLM's rule, applied to the same row, keeps (9, -0.25, 1). The packed class raises ValueError: Expected one selected token and rank per position. The exception leaves process_outputs, and vLLM's output loop has no per-request catch around it.

The fix — proposed, not in the PR

Where the fix lands: RL only, one line in patches.py update, plus a 3-column test case in test_hook_only_changes_eligible_requests and the real-vLLM test (test_vllm_patches.py:1073), which today only feeds 1-column rows. No vLLM change.

The fix, as pseudocode (proposed; the slice was run on CPU, not on a GPU)

# generation actor, vLLM output loop (one task, every engine step)
def update(rows):
    ids, vals, ranks, _ = rows                    # ids [1, 3] here
    before = len(history)
    history.append_arrays(ids, vals, ranks)       # raises on width 3
    history.append_arrays(ids[:, :1], vals[:, :1], ranks)  # keep column 0, like native
    cumulative = history.cumulative_after(cumulative, start=before)

With the slice, the same run stores [-0.5, -0.25], which matches native. append_arrays keeps its 1-column check, so a wrong caller still fails loudly.

The consequence. As written, one top-k request on the same engine, captured or not, fails every in-flight request on that frontend and stops it serving. Fix the slice before merge. Then run the PR's unchecked “captured serving smoke” box with a top_logprobs=0 captured request running alongside a top_logprobs=2 request.
