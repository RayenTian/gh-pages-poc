Six pages on this PR — this one: the Megatron-LM code RL depends on, and where it should live.

The shared-prefix forward needs one input that ordinary packing doesn't: which tokens are the prompt and which are each completion. #8156 defines that input as a small dataclass in megatron.core. Everything that builds it lives in #8152, under megatron.rl: matching prompts, binning under a token budget, sharding across DP ranks, and building the token and position tensors. megatron.rl is Megatron's own RL code and isn't in the wheel, so #8158 ships a slice of it just for this PR. None of the 8 modules imports anything from megatron.core. They use only the standard library and torch.

What does the data structure look like?

It's a frozen dataclass of lengths, the same idea as PackedSeqParams for ordinary packing. Here are both, with the real values for one small group: one prompt of 6 tokens and two completions of 3 and 2. The values come from running #8152's planner and #8156's layout on CPU.

Ordinary packing (in core today)

# megatron/core/packed_seq_params.py @dataclass class PackedSeqParams: qkv_format: str # "thd" cu_seqlens_q: Tensor # row starts max_seqlen_q: int ... # CP group, padding # the two rows, prompt copied into each: PackedSeqParams(qkv_format="thd", cu_seqlens_q=[0, 8, 17], max_seqlen_q=9) # 17 tokens in the forward

Shared prefix (#8156, in core)

# megatron/core/shared_prefix_layout.py @dataclass(frozen=True) class SharedPrefixLayout: # one star prefix_len: int completion_lens: Sequence[int] logical_completion_lens: ... = None padding_multiple: int | None = None @dataclass(frozen=True) class SharedPrefixForestLayout: # stars in one forward roots: tuple[SharedPrefixLayout, ...] mtp_loss_group_root_counts: tuple[int, ...] = () SharedPrefixLayout(prefix_len=6, completion_lens=(3, 2)) # 11 tokens; .position_ids() = [0..5, 6,7,8, 6,7]

Utilities that build it. Core gives the layout a few methods: position_ids(), cp_local_indices() and padded_token_multiplicities(). Getting from training rows to that layout takes three calls, all in #8152. These are what RL actually imports:

# 1. one record per row (megatron.rl.shared_prefix_tensors) rows = build_shared_prefix_rows(input_ids=..., input_lengths=..., prompt_lengths=[6, 6], group_ids=["g0", "g0"]) → [SharedPrefixRow(row_index=0, group_id="g0", prompt_token_ids=(101..106), completion_length=2), SharedPrefixRow(row_index=1, group_id="g0", prompt_token_ids=(101..106), completion_length=3)] # 2. group rows into forwards (megatron.rl.shared_prefix_execution) units = plan_shared_prefix_execution_units(rows, bin_capacity=64, padding_multiple=1) → (SharedPrefixExecutionUnit(row_indices=(1, 0), physical_length=11, shared_layout=megatron.rl.SharedPrefixLayout(group_id="g0", prompt_token_ids=(101..106), row_indices=(1, 0), completion_lengths=(3, 2))),) # 3. gather tokens and build index maps (megatron.rl.shared_prefix_tensors) bin = materialize_shared_prefix_layout(input_ids, input_lengths=..., layout=units[0].shared_layout) → packed_input_ids [101 102 103 104 105 106 | 301 302 303 | 201 202] position_ids [ 0 1 2 3 4 5 | 6 7 8 | 6 7] completion_scatter_columns [5 6 7 5 6] # where each logprob goes back in its row

Note the struck name: #8152 has its own SharedPrefixLayout and SharedPrefixForestLayout, with the same names as core's but different fields. RL then copies one into the other field by field before the forward (train.py#L260-L301).

A naming clash. In #8152 and #8156, a forest means several stars packed into one forward. NeMo-RL already uses forest training for something else: one rollout that owns several training rows (after compaction, or with sub-agents and branches). A reader who sees both will assume they are linked. Better names: star for one prompt with its completions (unchanged), star pack for several stars in one forward (SharedPrefixStarPack), and prefix tree for deeper sharing. A prefix tree is different from the call tree that call selection reads from parent links.

Where each module would go

Megatron already has a home for this kind of code. The scheduler that plans ordinary packed batches across DP ranks and builds PackedSeqParams lives in core, in megatron/core/datasets/data_schedule.py. The worker-side half of #8152 is the same kind of code. The driver-side half runs before any model exists, so it goes to RL. Otherwise the driver would import megatron.core, whose __init__ loads parallel_state and DDP.

So what. RL needs about 2,600 lines of packing code. None of it touches megatron.core, but it ships from a package that isn't in the wheel and isn't a product. Following the PackedSeqParams / data_schedule.py pattern removes #8158 and RL's last megatron.rl import. It also removes the duplicate layout types and the cross-repo contract test. The RL driver then needs no Megatron install at all.
