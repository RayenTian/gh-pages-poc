Four pages on #5097, one question each; the first chip is an earlier PR in the stack. This one: does Megatron run a Gym call through the same steps as vLLM?

Background. A Gym call is one chat turn from an agent. TQ holds what the model actually saw and wrote. Each call does at most one read (the earlier turns' exact token ids, the prefix) and one write (this call's tokens). Behind Dynamo, the KV router needs final token ids, so the read moves to the frontend. Dotted words: hover or tap.

# token_capture.py, called by native stage() and by the Dynamo adapter
def _stage_call(admission, *, prompt_ids, gen_ids, logprobs, policy_epoch, routes, media):
    call = None
    try:
        call = begin_call(CaptureAdmission.model_validate(admission),
                          weight_version=_weight_version(policy_epoch))   # inside the try now
        return complete_call(call, prompt_ids, gen_ids, logprobs,
                             extras=routed_experts(routes),        # C2: no more extras=None
                             attachments=media)
    except Exception:                                              # C3: as native stage()
        return fail_call(call) if call else None                 # None → answer the call, no coords

So what. For text-only Gym calls, Megatron behind Dynamo already reads TQ the same way vLLM does, and its "begin after generation" matches aggregated Megatron. The real gap is the write: a second copy that drops routes and fails differently. One shared Megatron staging function fixes both. Moving all three steps into one module shared with vLLM is the longer-term goal, and fits the refit and worker cleanup tracked in #5413.
