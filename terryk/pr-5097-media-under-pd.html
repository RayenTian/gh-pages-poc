Four pages on #5097, one question each; the first chip is an earlier PR in the stack. This one: once images are allowed, who writes them to TQ, and how do they get there?

Background. For an image, the HF processor turns raw pixels into model inputs. Training needs those exact inputs, so the TQ write stores them with the call's tokens. With prefill/decode, the prefill engine runs the vision encoder; the decode engine only imports the finished KV cache and writes the answer, and is the one that writes to TQ. Dotted words: hover or tap.

Two checks for the multimodal PR: (1) decode imports prefill's KV by block hash, so two prompts with the same token ids but different images must not share blocks — confirm Megatron-LM's block hash covers the image, not only block_hash_salt; (2) #5097's adapter still marks the "decode gets the frontend's extra_args" fact as a DRAFT assumption (adapter.py L198); it holds at the pinned Dynamo nightly, so the note can cite the router code instead.

So what. Images need no new transport under prefill/decode. Dynamo already gives the decode leg the frontend's request extras, so the frontend's processed pixels reach the engine that writes TQ, just as they reach the single engine today. The multimodal PR should keep the one write on decode, check the block hash, and lift the two text-only refusals (#4912's processor check and #5097's media check).
