Six pages on this PR — this one: a small side fix in how split rows are put back in order.

Background. Before a forward pass, the driver splits the batch across data-parallel ranks. To keep work even, it can shuffle which rows go where. If the ranks' results come back joined rank after rank, they are no longer in the original order. BatchedDataDict.reorder_data(list) puts them back. It needs one list: for each slot in the joined result, which original row it came from.

The change, as pseudocode

Main

# driver: shard_meta_for_dp, after splitting rows across ranks src = [2, 0, 3, 1] # joined slot j came from original row src[j] back = [0] * 4 for slot, row in enumerate(src): back[row] = slot # the inverse: [1, 3, 0, 2] return per_rank_rows, back # comment says "same as _shard_for_logprob"; it isn't

This PR

# driver: shard_meta_for_dp src = [2, 0, 3, 1] back = invert(src) return per_rank_rows, src # the form reorder_data expects

Real code: main preshard.py#L166 → PR preshard.py#L244. The older non-TQ path already returns the right form: shard_by_batch_size returns batch_sorted_indices, and lm_policy.py#L824 passes it to reorder_data.

Why nothing broke

Every caller of shard_meta_for_dp drops the second value with metas, _ = …: tq_policy.py#L521, #L647, #L804, tq_value.py#L127, #L183, #L243 and teacher_worker_group.py#L376. On the TQ path, each worker writes its results back under each row's own key, so order never matters there.

So what. This is a correct fix to a value nobody reads, so it can't change training. It isn't about shared prefixes, so the PR description should mention it. The simpler fix is to stop returning a value that nobody reads.
