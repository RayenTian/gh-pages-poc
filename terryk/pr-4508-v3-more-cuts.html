Five pages on this PR. The round-1 pages describe an older head. This one: what round 3 adds to the round-2 cuts.

When a checkpoint cuts generation, each unfinished model call becomes one row, and the new stage_generation_prefix_batch writes many rows to TransferQueue (NeMo-RL's in-memory store) at once. It first sorts the rows by a signature: each column's name, type, and size past the token axis (L816-L820), then writes one group per call. But its only caller, _cut_batched.stage(), hands it rows from one worker's cut, and those rows always agree on every part of the signature.

Why one worker's cut is always one group (C15)

So the grouping code (L806-L838) never splits a real cut. If rows ever did differ in type or size, stack_or_nest would raise before anything is written, and stage() already writes each row alone after a failed batch. The one case that would go wrong without a check is a column that some rows have and others lack: the batch takes its column names from the first row, so the extra column would be dropped with no error. The simpler version keeps one check for that.

The change — proposed, not in the PR

Where the fix lands: RL only, one function. stage_generation_prefix_batch in data_plane/tq_token_sink.py, plus three tests in test_tq_token_sink.py. No caller change: it returns the same keys in the same order.

The team also looked for a smaller design and found none: the read batcher has no twin in the repo, and holding each call's lock across the shared write needs the generator shape the PR uses. Ideas that did not hold up were left out. One example is the cleanup of written rows that no call received. It looks like dead code, but it still runs when rolling back a call fails.
