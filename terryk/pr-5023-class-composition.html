Design smell: what mirrors and what doesn't

  • Mirrors: the frontend after #5097. One NemoRLChatEngine holds a ChatBackend (VllmChatBackend or MegatronChatBackend), and each render process holds a RenderWorker (VllmRenderer or MegatronRenderer). Same shape, one class per engine. Tokenization happens here for both.
  • Doesn't mirror: the adapter in #5023. vLLM's adapter holds the worker (_host) and calls its methods. Megatron-LM's adapter holds no worker. So it opens its own InferenceClient to a coordinator the worker already has a client for, and gets KV events and "ready" through a ZMQ push/pull pair between two threads of the same process. That pair is the only reason for the two picked ports (C5).
  • Subclassing across repos: #5097's NemoRLMegatronLLMEngine subclasses Megatron-LM's class and overrides its private _stream_chunks, catching the final record through a context variable (_FinalTee). It breaks quietly if Megatron-LM renames that method. #5097 C5 asks to fold it into C1's adapter.
  • Native step skipped: in B, nothing a rollout runs is NeMo-RL's own worker code, so capture, routed experts and generation cuts each need separate work (#5097's refusals). In A and C the adapter calls the native step, so they come with it.
  • After C1: A and C line up box for box: Worker → adapter on DynamoEngineAdapter → worker method → engine. What is left: Megatron's prefill/decode handoff (serve_prefill, release_handoff), which needs Megatron-LM to make its private release and claim calls public (example). The extra coordinator process is Megatron's own and stays in native generation too.

The shape test: in a good design, swapping the engine changes only the boxes that touch the engine. After #5097 that holds for the frontend. In this PR it does not hold for the engine actor, where four objects (an adapter, a client, a reporter and a receiver) differ from vLLM's one. C1 brings it back to one.
