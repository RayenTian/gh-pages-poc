Three pages on this PR. This one: which lines can go, and why each cut is safe.

The biggest piece is the writer actor's transport. pack_columns / unpack_columns turn each column into NumPy bytes for the trip to the actor, and RayPrefixWriterClient wraps the actor. But the sink already knows how to call an actor: _call_dp does ray.get(method.remote(...)) when given an actor handle, and Ray pickles a TensorDict with jagged and bf16 columns exactly (checked on the pinned torch, tensordict and Ray versions, not through a live actor). The PR body itself says the packing "did not improve total snapshot latency".

So what. The three speedups the PR measured all survive: the column encoder, the prepare/write overlap and the separate writer process. What goes is transport code Ray already provides, metrics nothing reads, and config that repeats existing knobs. The PR would then be about +1,770 lines. A further option is to split it: encoder + pipeline first (the bigger win), then the writer actor.
