vLLM today
On main, each vLLM engine answers Dynamo through NeMo-RL's own adapter, which calls the native vLLM worker. Token capture, routed experts and generation cuts all go through that worker.
This PR
Each Megatron engine answers through Megatron-LM's adapter instead. It reaches the engine through the engine's coordinator, over sockets, and #5097 later has to turn routed experts and generation cuts off on that path.
After C1
Proposed, not in the PR. A NeMo-RL DynamoMegatronAdapter on the same base class as vLLM, calling the native Megatron worker. A draft shows it as real code: terrykong/RL#58.

Three pages for this PR. The ★ page links every page in the stack.

Background. Dynamo's frontend sends each request to a Worker running inside an engine process. The Worker hands it to an adapter, the class that knows how to run a request on that engine. On main, NeMo-RL writes that class once (DynamoEngineAdapter) and vLLM fills in four methods. In prefill/decode serving, one engine reads the prompt and hands its KV cache to a second engine that writes the answer; the handoff is the step this stack adds. Dotted words have a short explanation: hover or tap them.

Same example in all three columns: one completion request, prompt token ids [1, 2, 3], 2 new tokens. The Megatron columns use one prefill and one decode engine.

Rank 0 serves the engine — this PR

# Ray call on rank 0; the adapter runs as a task on the engine's inference loop
def start_dynamo_endpoint(namespace, engine_env, …):
    event, system = pick free ports in [4000, 4100)   # released, bound later (C5)
    os.environ |= engine_env + {DYN_SYSTEM_PORT: system}
    cfg = Config(external mode, role, event port, …)
    run on inference loop: Worker(MegatronLLMEngine(cfg)).run()
# second Ray call, every rank
def attach_dynamo_events(addr):
    reporter.connect(addr); reporter.send("ready", coordinator address)

What the review asks, and what the draft shows

C1 asks for the right-hand column: one adapter shape for every backend, so Megatron runs capture and generation cuts through its own worker the way vLLM does, and the later PRs shrink (#5025 uses main's rollout_client, #5097 drops its two refusals). C5 asks that the two picked ports not come along. The draft PR is there so the difference is visible as code, not to be merged.

What in the draft is real and what is not: start, serve_rollout (plain and decode-with-handoff), serve_prefill, abort and kv_event_sources call real Megatron code. Two steps are stubs, release_handoff and the decode-side claim, because Megatron-LM keeps the RELEASE_KV / CLAIM_KV messages in private methods of MegatronLLMEngine; the draft names them, and they need one small upstream change that turns them into functions. The CPU unit tests pass (75) against stand-ins for the Linux-only Dynamo package; nothing ran on a GPU.
