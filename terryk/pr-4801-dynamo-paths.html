Pages on this design, one question each. This one: how the Megatron switch fits next to main's Dynamo path.

Before
On main, dynamo: true means NeMo RL's own vLLM workers behind a Dynamo frontend (#4905, merged). Main's config check allows it only for backend: vllm.
This PR
Lets dynamo: true also mean Megatron prefill/decode engines, adds their config and engine-width math, and teaches refit about shards of different widths. The switch itself is refused until #5025.
Status
Open — the backend checks now agree; two things are left. Main still rejects this PR's control_timeout_s as "removed" (review comment C9), and part of the Megatron config is a hand copy of main's (C10).
Background. Dynamo puts one HTTP frontend in front of many inference engines and routes each request. A prefill/decode split runs prompt reading and answer writing on different engines. A refit pushes new weights from the trainer into the engines after every step. Dotted words have a short explanation: hover or tap them.

Three ways Dynamo has fronted NeMo RL's engines

All three end at a Dynamo frontend. They differ in who owns the engine workers. The first was removed by #4905. The second is main today. This stack adds the third, using the same dynamo: true switch.

C9. This PR adds dynamo_cfg.control_timeout_s for Megatron. #4905 put the same key on main's list of removed keys, and the check ignores the backend. It runs first at startup (run_grpo_single_controller.py), so a Megatron config that sets the field stops with "refit and pause use the vLLM backend's own controls".

C10. MegatronDynamoFrontendArgs repeats five fields of main's DynamoFrontendArgs, and dynamo_enabled is defined twice. This PR's Dynamo 1.8 commit already had to copy main's changes over by hand.

What this PR changes now: refit with shards of different widths

The refit NCCL group lists the trainer ranks first, then each engine's ranks, shard by shard. Until now every shard had the same width, so shard i started at i × width. A prefill engine at TP 4 next to decode engines at TP 2 breaks that. RefitMembership.worker_offset() adds up the earlier widths instead, dead shards included, because the worker list never shrinks.

workers_per_shard = (4, 2, 2) # 1 prefill at TP 4, 2 decode at TP 2; 8 workers workers: 0 1 2 3 | 4 5 | 6 7 shard: 0 | 1 | 2 worker_offset(0, 1, 2) = 0, 4, 6 # an equal-width rule (i × 2) would give 0, 2, 4: wrong shard 0 dies → refit ranks after the trainers: shard 1 → 0..1, shard 2 → 2..3

All four call sites switch to it: the Megatron path and three vLLM paths. With equal widths the result is the same as before:
