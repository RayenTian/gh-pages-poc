Pages on this design, one question each. This one: how the Megatron switch fits next to main's Dynamo path.

Before
On main, dynamo: true means NeMo RL's own vLLM workers behind a Dynamo frontend (#4905, merged). Main's config check allows it only for backend: vllm.
This PR
Lets dynamo: true also mean Megatron prefill/decode engines, adds their config and engine-width math, and teaches refit about shards of different widths. The switch itself is refused until #5025.
Status
Open — the backend checks now agree; two things are left. Main still rejects this PR's control_timeout_s as "removed" (review comment C9), and part of the Megatron config is a hand copy of main's (C10).
Background. Dynamo puts one HTTP frontend in front of many inference engines and routes each request. A prefill/decode split runs prompt reading and answer writing on different engines. A refit pushes new weights from the trainer into the engines after every step. Dotted words have a short explanation: hover or tap them.

Three ways Dynamo has fronted NeMo RL's engines

All three end at a Dynamo frontend. They differ in who owns the engine workers. The first was removed by #4905. The second is main today. This stack adds the third, using the same dynamo: true switch.

C9. This PR adds dynamo_cfg.control_timeout_s for Megatron. #4905 put the same key on main's list of removed keys, and the check ignores the backend. It runs first at startup (run_grpo_single_controller.py), so a Megatron config that sets the field stops with "refit and pause use the vLLM backend's own controls".

C10. MegatronDynamoFrontendArgs repeats five fields of main's DynamoFrontendArgs, and dynamo_enabled is defined twice. This PR's Dynamo 1.8 commit already had to copy main's changes over by hand.

What happens at startup with dynamo: true — before, after, and the C9 fix (proposed)

Three checks run in order on the driver before any engine starts. Before this PR, a Megatron config with dynamo: true stopped at the second one. After it, the config gets through the backend checks and is refused on purpose by MegatronGeneration until #5025 builds the engines. On the way, it now requires P/D: there is no Megatron + Dynamo without disaggregation, while vLLM + Dynamo on main has no P/D yet.

The fix for C9, as pseudocode (proposed, not run)

Where the fix lands: RL only, one function. reject_outdated_dynamo_backend skips the key for Megatron; plus one test case and one docs line. The vLLM migration message stays.

# driver, inside check_outdated_config
def reject_outdated_dynamo_backend(config):
    for key, why in REMOVED_DYNAMO_CFG_KEYS:                               # includes control_timeout_s (L222)

        if key in dynamo_cfg: problems.append(f"{key} was removed: {why}")

Refit with shards of different widths — before and after

The refit NCCL group lists the trainer ranks first, then each engine's ranks, shard by shard. Before, every shard had one width, so shard i started at i × width. A prefill engine at TP 4 next to two decode engines at TP 2 breaks that, so this PR keeps one width per shard and adds the earlier widths up. Dead shards still count, because the worker list never shrinks.

Refit plan, before (main)

# driver, weight synchronizer: plan the refit group (also after a shard dies)
def plan_refit_membership(surviving, dp_size, total_workers, trainers):
    width = total_workers // dp_size                          # one width for every shard
    prefix = {s: i * width for i, s in enumerate(surviving)}  # ranks after the trainers
    return Membership(world=trainers + len(surviving) * width, prefix, width)
# driver, fan out the new group
vLLM:     leader = workers[shard * width]                     # first worker of the shard
Megatron: ranks for workers[shard * width : + width]

Refit plan, after (this PR)

# driver, same place; example: 16 trainer ranks, shards (4, 2, 2), shard 0 dead
def plan_refit_membership(surviving, dp_size, total_workers, trainers,
                          shard_widths=None):                        # no caller passes it yet
    widths = shard_widths or (total_workers // dp_size,) * dp_size   # (4, 2, 2)
    prefix = {s: i * width for i, s in enumerate(surviving)}
    for s in sorted(surviving): prefix[s] = next; next += widths[s]  # {1: 0, 2: 2}
    return Membership(world=trainers + next, prefix, widths)         # world = 16 + 4 = 20
def worker_offset(shard): return sum(widths[:shard])                 # 0, 4, 6: dead shards count
vLLM:     leader = workers[membership.worker_offset(shard)]          # C5: tested only with equal widths
Megatron: ranks for workers[worker_offset(shard) : + widths[shard]]

Real code: plan_refit_membership, RefitMembership.worker_offset, vLLM rebuild_collective (also L1288, L2033), Megatron _refit_ranked_workers. With equal widths the result is the same as before. No caller passes uneven widths until #5025's engine fleet does.
