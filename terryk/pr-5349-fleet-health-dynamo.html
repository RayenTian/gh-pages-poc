How fleet health keeps Dynamo's frontends off a lost generation shard

NVIDIA-NeMo/RL #5349 · replaces #4955 · all links pinned to head 99b65276c5

Before
Turning on fleet health with policy.generation.dynamo: true stopped the run at startup (the refusal, linked at the base).
This PR
The controller tells the generation backend which shards are in service. Behind Dynamo, each engine then takes itself out of, or back into, the frontends' list of engines.
Status
New behavior, works in the author's GB200 runs. One review ask is open: no CI job runs the new register/unregister calls (comment C11).
Background. A shard is one vLLM engine (here: 3 of them, numbered 0, 1, 2). Fleet health probes each shard every 5 s and keeps a list of shards that may get requests. Behind Dynamo, requests go to frontends, and the frontends pick the engine from a list in etcd, not from NeMo RL's list. Dotted words have a short explanation: hover or tap them.

Both paths start from the same fact: the fleet monitor's serving_shards(). Natively, NeMo RL picks the engine for every request from that list (fleet_selector.next_shard()), so a shard off the list gets nothing. Behind Dynamo nobody read that list, so the frontends kept sending to a dead shard. This PR copies the list into etcd: after every probe and before every resume, the controller calls the new hook set_serving_shards, and each engine whose state changed adds or removes its own etcd entry.

The change, as pseudocode

Before: startup refused the combination

# driver, at startup
def validate_settings(cfg):
    if dynamo and fleet_health.enabled:  # refused before this PR
        raise ValueError(...)            # "the frontend picks engines itself"

After, 1 of 3: the controller pushes the list

# SingleController event loop: the probe pump and every refit
async def _gen_fleet_probe_pump():               # every probe_interval_s (5 s)
    probe every shard; fold results into the fleet monitor
    if not recovering_from_refit:                # skipped mid-recovery
        await _push_serving_shards()

async def _sync_weights():   # the refit
    pause; transfer weights; mark shards healthy
    await _push_serving_shards()                 # before resume, so a returned shard
    resume generation                            # gets requests at once

async def _push_serving_shards():
    async with lock:                             # one push at a time
        await to_thread(gen.set_serving_shards,  # in a thread
            serving=monitor.serving_shards(),    # {0, 2}
            quarantined=dead_or_retired,         # {1}: DEAD or RETIRED only
            timeout_s=probe_timeout_s)           # 2 s

After, 2 of 3: the backend asks only the shards that changed

# VllmGeneration.set_serving_shards (a no-op without Dynamo)
routed = _dynamo_routed_shards                               # {0: leader0, 1: leader1, 2: leader2}
for shard whose leader was replaced: del routed[shard]       # restarted: drop, no call yet
calls = {s: leader(s).set_dynamo_routed_async(s in serving)  # {0,2} ^ {0,1,2} = {1}
         for s in serving ^ routed}
ray.wait(calls, timeout=timeout_s)                           # wait up to 2 s
for shard, result in calls:                                  # shard 1:
    ok and leaving   -> del routed[shard]                    #   answered: unregistered
    ActorDiedError   -> del routed[shard]                    #   dead process: lease drops it
    else, quarantined -> ray.kill(its workers)               #   silent + quarantined
    else             -> keep, retry                          #   anything else: next push asks again

After, 3 of 3: the engine edits its own etcd entry

# engine process, its asyncio loop (DynamoEngineAdapter)
async def on_endpoint_ready(endpoint):                        # Dynamo's Worker calls this once
    self._endpoint = endpoint                                 # before it registers
async def set_routed(routed):
    if routed == self._routed: return                         # already there: nothing to do
    if routed: await endpoint.register_endpoint_instance()    # back in every frontend
    else:      await endpoint.unregister_endpoint_instance()  # requests in flight finish

Also new: behind Dynamo the probe itself (is_alive) fails when the engine's Dynamo endpoint stopped or vLLM reports its engine core dead, because a failed call through a frontend does not say which engine failed it. The Dynamo calls were checked against Dynamo's source at the commit matching the pinned 1.8 nightly.

Where the two paths still differ

Native vLLMBehind Dynamo
Shard 1 stops getting requestsOn the next request after it is marked DEADIn the same probe round, if it answers; up to 30 s later if its process is gone
A DEAD shard that does not answerLeft runningIts workers are killed (DEAD never comes back without a restart, so nothing is lost)
An engine that hangs without dyingSeen through failed requestsNot seen (a follow-up PR, per the PR description)
So what. Fleet health now works with Dynamo, and NeMo RL's list of shards in service becomes the frontends' list within one probe. The one gap the review asks to close: CI runs this lane with a single shard, so the push never changes anything there, and the register/unregister calls are tested only by the author's hand runs. The author already has a 2-GPU check against real frontends; committing it as a fast CI test would cover the new path.
