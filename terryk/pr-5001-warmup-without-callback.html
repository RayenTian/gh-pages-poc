Can setup start the trainer warm-up without a callback class?

NVIDIA-NeMo/RL #5001. All permalinks pin the PR head 5223071.

Before
No warm-up. Step 1 pays for compiling and tuning the trainer's kernels.
This PR
Adds an opt-in warm-up: one fake step on the trainer while vLLM loads or the first rollouts run. Setup starts it with an 80-line class, _EarlyTrainerWarmup, hung on the trainer build as a done-callback. Whether to warm up is decided twice, in setup and in the controller.
Status
Proposed — not implemented. Review comment C8 asks for a plain wait in setup and a single decision handed to the controller. The warm-up starts at the same moment in every case, so the speedup is the same.
1 · what the switches change 2 · warm-up crash with CUDA graphs 3 · warm-up without a callback

Three pages on this PR. Page 1 explains all the switches; this one is only about how the warm-up (switch ④) is started.

Background. The warm-up can start in two places. If the trainer finishes building before vLLM has loaded, setup starts it, so it runs while vLLM loads. Otherwise the controller starts it beside the first rollouts, and step 1 waits for it. C8 changes only code that runs after the dataset has loaded. Switch ① still submits the trainer build before the vLLM reserve, exactly as in the PR.

PR head: the class it calls

# runs on whichever thread finishes the trainer build
class _EarlyTrainerWarmup:
    def start(self, trainer_future):                              # the done-callback
        try:
            if gen_future is None or not gen_future.done():       # vLLM still loading?
                self.refs = trainer.start_warmup_first_pass(...)  # non-blocking: Ray futures
        except Exception as e:
            self.error = e                                        # a callback's errors are only logged
        finally:
            self.started.set()                                    # threading.Event

# setup thread
    def finish(self):
        self.started.wait()                                       # result() can return before start() ran
        if self.error: raise self.error                           # re-raise on the setup thread
        if self.refs is None: return False                        # vLLM won; the controller does it
        ray.get(self.refs)
        return True

Real code: _EarlyTrainerWarmup, callback attached, finish called.

Three of the class's parts exist only because the start is a callback: the stored error (a callback's exceptions are only logged), the threading.Event (result() can return before the callback has run), and the class itself, which carries state between the two threads. Two things are also written twice: the skip check (setup, silent; controller, printed) and the step's field list (controller; trainer_warmup_kwargs). Both helpers live in the 5,275-line single_controller.py, and setup imports them back inside a function to avoid an import loop.

The fix, as pseudocode (proposed, not run): setup

Where the fix lands: RL only, three files. setup.py loses the class and decides once; single_controller.py reads that decision; advantage_stage.py holds the one field list. No Megatron worker change: its own skip check covers model settings the driver cannot see, so it stays.

def _trainer_warmup_kwargs(cfg, stage_cfg, step):

Why it is the same speed

  • ① is untouched. The trainer build is still submitted before the reserve. Every row of the figure starts it at time zero.
  • A, trainer first. The PR's callback is attached after the dataset load and fires when the trainer is ready. C8's wait sits in the same place and returns at the same moment.
  • B, vLLM first. Both skip the setup start, and the controller runs it beside the first rollouts.
  • C, rebuild. Both run after the rebuild, so only the final trainer is warmed up. (Starting it inside the build task would warm the thrown-away trainer. That is why C8 waits in setup instead.)
