Can setup start the trainer warm-up without a callback class?

NVIDIA-NeMo/RL #5001. All permalinks pin the PR head 5223071.

Before
No warm-up. Step 1 pays for compiling and tuning the trainer's kernels.
This PR
Adds an opt-in warm-up: one fake step on the trainer while vLLM loads or the first rollouts run. In setup it is started by an 80-line class, _EarlyTrainerWarmup, hung on the trainer build as a done-callback.
Status
Proposed — not implemented. The review asks to replace the class with ~12 plain lines in setup. Same start time in every case, so the same speedup. Not yet a staged review comment (would be C8).

Three pages on this PR. Page 1 explains all the switches; this one is only about how setup starts switch ④.

Background. The PR's warm-up (switch ④ on page 1) can start in two places. If the trainer finishes building before vLLM has loaded, setup starts it, so it runs while vLLM loads. Otherwise the controller starts it beside the first rollouts, and step 1 waits for it. A flag, trainer_warmup_ran, tells the controller not to run it twice. Only the setup start changes on this page.

The setup start, as pseudocode

PR head: setup thread

PR head: the class it calls

# runs on whichever thread finishes the trainer build
class _EarlyTrainerWarmup:
    def start(self, trainer_future):                              # the done-callback
        try:
            if gen_future is None or not gen_future.done():       # vLLM still loading?
                self.refs = trainer.start_warmup_first_pass(...)  # non-blocking: Ray futures
        except Exception as e:
            self.error = e                                        # a callback's errors are only logged
        finally:
            self.started.set()                                    # threading.Event

# setup thread
    def finish(self):
        self.started.wait()                                       # result() can return before start() ran
        if self.error: raise self.error                           # re-raise on the setup thread
        if self.refs is None: return False                        # vLLM won; the controller does it
        ray.get(self.refs)
        return True

Real code: _EarlyTrainerWarmup, callback attached, finish called.

Three of the class's parts exist only because the start is a callback: the stored error (a callback's exceptions are only logged), the threading.Event (result() can return before the callback has run), and the class itself, which carries state between the two threads. Its skip check also returns None without saying why, while the controller's copy prints the reason.

The fix, as pseudocode (proposed, not run)

Where the fix lands: RL only, one file, setup.py. The class goes. Nothing in the controller or the Megatron worker changes.

# setup thread, setup_single_controller (proposed, not run)
...dataset load, and the trainer rebuild if the dataset caps max_num_steps...
early_warmup = _EarlyTrainerWarmup.maybe_create(cfg, loss_fn, ...)
if early_warmup:
    submitted['trainer'].add_done_callback(early_warmup.start)
warmup_kwargs = warmup_kwargs_or_none(cfg)                         # one skip check; prints the reason
gen_f, trainer_f = submitted['generation'], submitted['trainer']
refs = None
if warmup_kwargs is not None:
    wait([gen_f, trainer_f], return_when=FIRST_COMPLETED)          # sleep until one build is done
    if trainer_f.done() and not gen_f.done():                      # same test start() makes
        refs = trainer_f.result()[0].start_warmup_first_pass(...)  # non-blocking
generation = gen_f.result()                                        # vLLM keeps loading; warm-up runs
trainer    = trainer_f.result()                                    # build errors raise here, as before
if early_warmup:
    trainer_warmup_ran = early_warmup.finish()
if refs is not None:
    ray.get(refs)                                                  # warm-up errors raise here, normally
    trainer_warmup_ran = True
class _EarlyTrainerWarmup: ...                                     # whole class, ~80 lines, removed

Real calls it uses: start_warmup_first_pass (returns Ray futures, does not block), trainer_warmup_skip_reason. wait and FIRST_COMPLETED are from Python's concurrent.futures; they work across the two thread pools.

Real code: _maybe_start_trainer_warmup, called, awaited before step 1.

Why it is the same speed

  • A, trainer first. The PR's callback fires when the trainer build ends. C8's wait returns at the same moment. Both start the warm-up then, and both make setup wait for it after vLLM is up.
  • B, vLLM first. Both skip the setup start. The controller runs it, unchanged.
  • C, rebuild. The PR attaches the callback after the rebuild. C8's code sits in the same place, so it also warms only the final trainer. (Starting it inside the build task would warm the thrown-away trainer. That is why C8 waits in setup instead.)
So what. The same speedup, with no callback, no Event, no stored error and no class. Errors reach setup the normal way, and the skip reason is always printed. The two start places and the trainer_warmup_ran flag stay, because each start covers a different order. Nothing here has been run; the PR still has no timings for any switch (page 1).
