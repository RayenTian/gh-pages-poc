How one checkpoint cut reaches calls spread over several vLLM HTTP frontends

PR #5267 · stacked on #5176 · permalinks pinned to head 955c92cd (this PR) and d42cf304 (the PR below it)

Before
A worker with more than one HTTP frontend refused prefix cuts at setup. Only a single frontend could cut.
This PR
The frontend that gets Gym's cut call asks the other frontends, over a private local port, to cut the calls they serve. It then merges all the answers into one receipt.
Status
New feature, under review. The author's H100 run passed. No CI run uses more than one frontend yet, and the review asks for tests (links below).
Background. During an RL checkpoint, Gym asks each vLLM worker to save the tokens generated so far for every call still running. This is a generation cut. After a restore, a saved call resumes from those tokens instead of starting over. One worker can run several HTTP frontends that share one listening socket. A call's tokens live only in the frontend that took its request. Dotted words have a short explanation: hover or tap them.
Why it should be faster. Each frontend cuts only its own calls, and all frontends cut at the same time. So the cut's wall time is about the slowest frontend's share, not the sum. The TQ writes and Gym's own prepare/commit are the same amount of work. The author measured one run per setting (from the PR description): with the write pipeline on, the cut took 0.19–0.25 s with 1 frontend and 0.06–0.07 s with 4. Gym's pause barely moved (1.48 s vs 1.44 s), because the cut is now a small part of it. It is slower only when a frontend stalls: then the cut waits up to token_capture.control_timeout_s for it.

Same 3 calls, one frontend vs two

Gym's inventory names 3 calls: c1 is running on frontend A, c2 is running on frontend B, and c3 has not reached the worker yet. Gym's request lands on B, because the kernel picks a frontend on the shared socket.

At startup (new), the owner frontend collects every frontend's private URL and sends the full list to all of them, so any frontend can lead a cut. A frontend that errors or misses the timeout claims nothing: its calls get ✗ and regenerate after a restore. The checkpoint itself never fails.

QuestionAnswer from the code
Where do the two paths meet?Both run the same cut code, _checkpoint_steps / _cut_batched. The only difference is the claims_only flag: a call this frontend does not know becomes null (L604) instead of a failure ack. The merge turns a call nobody claims back into a failure, so one frontend's answer comes out the same either way.
Can the peer call go to another node?No. Each frontend binds its private port on 127.0.0.1 (L2867). All frontends of a worker live on one node.
Does Gym accept a merged receipt?Yes. Gym checks only that every inventory call has exactly one ack, in any order, matching that call. Nothing ties an ack to a frontend.
What else is now per frontend?Cut settings travel to child frontends with the capture command (L1084). flush also reaches children (L3382). Prefix counts are summed over frontends (L3390).

The route, as pseudocode

Before (one frontend only)

# the frontend's serving event loop
def generation_cut(inventory):
    check bearer token
    return run_cut(inventory)                   # unknown call → failure ack

After

# any frontend's serving event loop
def generation_cut(inventory):
    check bearer token
    if not peers:                                # 1 frontend: path unchanged
        return run_cut(inventory)
    claims = await gather(                       # all at once
        run_cut_claims(inventory),               # mine; null for the rest
        *[ask_peer(url, inventory) for url in peers])  # POST /claims on 127.0.0.1
    return merge_cut_claims(inventory, claims)     # running wins; unclaimed → failure

# ask_peer: timeout, HTTP error or bad answer
    → [null] * calls                             # that peer's calls regenerate

Real code: checkpoint_generation_cut, _peer_cut_claims, peers set at startup.

What the review asks

The design holds up: the merge is a small pure function, and Gym accepts the merged receipt as is. The open asks are about proof. No CI run turns on prefix cuts with more than one frontend. Two new paths (a stalled peer, and peers set at startup) can break without any test failing. The settings sent to child frontends are a hand-written copy of a function's arguments. That copy already went stale once in the PR below, and this PR fixes it.
