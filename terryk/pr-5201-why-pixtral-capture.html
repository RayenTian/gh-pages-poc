Why a Pixtral VLM could not use token capture, and what this PR adds

NVIDIA-NeMo/RL #5201 · feat(vllm): token capture for Pixtral (Mistral3) images · permalinks pin head 2fc3ba0 (before-the-PR links pin the merge base bb9ed78).

Before
Token capture only understood one image format: the Nemotron Omni processor. Turning it on for a Pixtral (Mistral3) model failed at setup, and even past setup the capture code would refuse every Pixtral image.
This PR
Teaches the vLLM worker and capture_processed_media to read Pixtral images and stage them in the same packed format Omni already uses, so the storage and trainer-side code stay unchanged.
Status
Worker side done; not usable from a run on main yet. The driver check in setup.py still refuses any VLM that is not Omni. The PR says so, and a code comment says so. A follow-up must open that check and give Pixtral a learner that reads the packed images.
Background: token capture. In GRPO the policy generates with vLLM, then the trainer computes log-probs on the same conversation. Without token capture, the trainer rebuilds the input: it re-tokenizes the chat and re-runs the image processor. If anything differs (pixels, image size, where the image tokens sit), the trainer scores a slightly different input than the one the policy saw. With token capture on, the vLLM worker stores the exact tokens and the exact processed pixels it used, and the trainer reads those. For a VLM this is how the learner sees the same pixels and image-token positions the policy did. Dotted words have a short explanation: hover or tap them.

The gap: Pixtral lays out image tokens in rows, Omni in one run

Two things stopped Pixtral. First, the worker's setup accepted only Omni's processor and raised Media capture requires vLLM's Omni dynamic-resolution processor (before, worker:907). Second, the capture code required an image's tokens to be one unbroken run (before, captured_media:479). Pixtral writes an image as rows of [IMG] tokens with a break token after each row, so it can never be one run. The PR's own test feeds a Pixtral prompt down the Omni path and gets exactly that rejection (test_omni_still_requires_one_contiguous_run).

Reading the shapes (one 56×84 image, from the PR's unit test, patch size 14, merge 2): [3, 56, 84] = [colors, height, width], raw pixels. · One [IMG] token covers a 28×28 cell (14 px patch × merge 2), so the image is 2 rows × 3 columns = 6 image tokens. · imgs [1, 24, 588] = [batch, patches, numbers per patch]: 24 patches of 14×14 pixels, 588 = 3 colors × 14 × 14.

Legend: green border = works, red border = refused, dashed = still missing. Numbers 0–5 are the order a run goes through.

How the PR closes the gap

Where it lands: RL only, two source files. vllm_worker_async.py picks the image family at setup and passes it on; captured_media.py reads Pixtral pixels and checks Pixtral's token rows. No change to the TQ sink or the reassembler: Pixtral is packed into the format they already read.

# vLLM worker, per chat call, off the event loop
def capture_processed_media(prompt, family, cast_dtype, merge):
    for image in prompt.images:
        if family == "pixtral":
            pixels = image.pixel_values.to(cast_dtype)          # fp32 → bf16, size = tensor's own H, W
            positions = where token == [IMG]                    # 6 of the 8 tokens
            require len(positions) == (H/28) * (W/28)          # 2 × 3 = 6
        else:
            pixels = image.pixel_values_flat
            require positions are one unbroken run      # the check Pixtral always failed
        require every position holds the image token
        imgs += pack_images(pixels)                      # [1, 24, 588] — same for both

Real code: _processed_pixtral_tensors, the Pixtral position check, the call site that passes the family and dtype.

So what. This is the worker half of Pixtral support. After it, a Pixtral image is captured, checked against its own size, and staged exactly like an Omni image, so nothing downstream of the worker changes. But a GRPO run on main still stops at the driver check in step 0. To train a Pixtral VLM with token capture, a follow-up must add Pixtral to that check and give it a learner that reads the packed imgs. The PR says this was tested end to end on an internal branch that already has those pieces.
