Two pages on this PR — this one: how the new run compares with a training run.

Background. A SingleController run has three parts: vLLM engines that generate, a trainer (Megatron workers on their own GPUs) that learns, and a refit that copies new weights to vLLM after each step. Dotted words have a short explanation: hover or tap them.

Both commands go through the same launcher, run_single_controller, and the same _train_pump. Setup makes one choice, no_op_trainer, and uses it to pick three things: which GPUs exist, which trainer object is built, and which weight transfer is built. The vLLM engines, NeMo-Gym, the sampler and the data plane are the real ones. The trainer-side steps (logprobs, advantages, training) are skipped or replaced by a timer.

One step, side by side (4 prompts × 2 answers = 8 rows)

QuestionAnswer
Where do the two runs split?Only in setup (clusters, trainer, weight transfer) and at the no_op_trainer branches in the train pump: logprobs, advantages and the train step.
What still differs after that?The vLLM engines never get new weights, so every step samples from the starting checkpoint. The train step's GPU time is a fixed number you choose (train_time_s), not a measurement.
Which settings does it refuse?Anything that needs a real trainer: PPO, checkpointing, on-policy distillation, refit-time quantization and more (validate_simulator_config). Setup stops before any engine starts.
Why keep both runs?The training run is the real thing. The simulator gives rollout timing (exposed generation, refit pauses) on only the vLLM GPUs, with the trainer's time set by hand.
So what. Generation, Gym, the sampler and the data plane are real, so rollout-side timing is meaningful. The trainer side is two timers. The simulator's own settings (num_steps, num_nodes) are applied on top of the recipe. The next page shows that num_nodes is applied too late, so values the recipe computes from the node count keep the old count.
