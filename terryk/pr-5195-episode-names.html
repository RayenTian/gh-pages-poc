Why Gym episode names repeat when flat rows go through the sync rollout path

NVIDIA-NeMo/RL #5195 (Gym submodule bump) · review comment C1 · permalinks pinned to 64e87dad1f (RL) and 23557b7c2a (Gym)

Before
The sync rollout path gave flat rows no task index. Gym's newer environment servers need one, so those rows failed.
This PR
Gives each flat prompt group a number from a new counter that starts at 0 in every process.
Status
Open — not fixed in this PR. The crash is fixed, but the numbers can repeat. Raised as review comment C1.
Background. NeMo Gym runs the environment for each rollout. For a flat row, Gym's single_agent_turn_legacy server names the episode "{task}-{rollout}", made from two numbers RL puts on the row. Gym uses that name as the key for its export files and its token capture. Dotted words have a short explanation: hover or tap them.

RL makes every prompt group's rows on the sync path in _prepare_nemo_gym_rows. This PR adds _unstamped_nemo_gym_task_indices, a module-level itertools.count(), and takes the next number from it for each flat group. Gym names the episode from that number unless the row carries its own _ng_rollout_id (app.py#L94-L97). Gym's own docstring warns: “Reused task and rollout indices produce a repeated capture key. Use an explicit id when numbering restarts across dispatches.” (episode_context.py)

Two ways the same name gets used twice

In A, the training rows come from the async collector, which numbers them with its own counter (trajectory_collector.py). Validation runs the sync path in the driver (grpo.py#L4953) and starts the new counter at 0, against the same Gym servers. In B, nothing saves the new counter, so a resumed sync run starts again at "0-0". Only servers running as single_agent_turn_legacy read these numbers; servers a recipe keeps as legacy_agent do not.

Sync path, before this PR

# driver process: sync GRPO, distillation, validation
def _prepare_nemo_gym_rows(rows, n):
    for i, row in enumerate(rows):
        row.group_id    = uuid of its prompt group
        row.rollout_idx = i % n  # no task index set

Sync path, after this PR

# driver process: sync GRPO, distillation, validation
_counter = itertools.count()                               # module level; 0 in every new process
def _prepare_nemo_gym_rows(rows, n):
    for g, group in prompt_groups(rows, n):
        if group already has a task index: keep it         # the async collector stamped it
        elif group has flat rows: idx[g] = next(_counter)  # C1: never saved, never shared
    for i, row in enumerate(rows):
        row.group_id    = uuid of its prompt group
        row.task_idx    = idx[g]
        row.rollout_idx = i % n
# Gym environment server, per row
name = row.rollout_id or f"{task_idx}-{rollout_idx}"       # the episode name

What would fix it — proposed, not in the PR

Where the fix lands: RL only, one function. _prepare_nemo_gym_rows in rollouts.py. No Gym change: Gym already prefers _ng_rollout_id over the numbers when a row has one.

Nothing below is implemented. For groups that got their number from the new counter, also set _ng_rollout_id from the group's uuid, the same format RL already uses for materialized rows (nemo_gym.py#L311-L318). Keep the task index too. Rows the async collector already numbered stay as they are.

The fix, as pseudocode (proposed, not run)

# driver process: same function, proposed change
        elif group has flat rows: idx[g] = next(_counter)
            from_counter.add(g)
    for i, row in enumerate(rows):
        row.task_idx    = idx[g]                                             # Gym still needs it to build the task
        if g in from_counter:
            row.setdefault("_ng_rollout_id", f"{group_id}-g{i}-t{attempt}")  # same format as materialized rows

Saving the counter in the checkpoint would fix B but not A: validation and the collector would still each count from 0.

So what. This does not crash or change training math. It mixes up Gym's records: export files and capture keys for validation (or for a resumed run) land on names that earlier episodes already used, so they can be overwritten or merged. The fix is about five lines in one RL function, plus a test that a new counter gives different names.
