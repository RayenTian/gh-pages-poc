Eight pages on this stack (#4905, #4979 and #5115), one question each. This one: what #5115 moves to several frontends, and why.

Before
One Dynamo frontend runs as a child process of the v2 (single controller) driver, on the driver's node. It holds one router, one session table (at most 65,536 Gym sessions) and every chat render. A small launcher patches Dynamo's code to plug in our chat engine, and checkpoint cuts go to a second port.
This PR
num_frontends frontends run on the GPU nodes, each started by a small Ray actor. They use stock dynamo.frontend with two supported plug-ins (our chat engine and the cut route), so the launcher and the second port are gone. The session table holds 16,777,216. A watchdog stops every service if its starter is killed.
Status
Open, under review. #4979 has merged, so this PR now targets main. The author still has to pin Dynamo 1.8.0 (it is a nightly today) and run two frontends on two different nodes. The review found no blocking bug; it asks for one small fix, one docs fix, two tests and run numbers (see below).
Background. Dynamo puts an HTTP frontend in front of NeMo RL's vLLM engines. Its router picks an engine, and the call travels to that engine over Dynamo's TCP request plane. etcd (service discovery) and NATS (events) let frontends and engines find each other. NeMo-Gym sends multi-turn chat calls and keeps each session on one engine. At a checkpoint, Gym posts a generation cut. Dotted words have a short explanation: hover or tap them.

Today vs this PR: processes, and one Gym call through each

The same example in both columns: 2 GPU nodes, 4 vLLM engines (e0–e3), and on the right num_frontends: 3 (F0–F2). Dashed boxes are OS processes; boxes inside them are the classes that do the work. ① to ⑤ is one Gym chat call; ✂ is a checkpoint cut.

What happens to one Gym call, step by step.

  1. ① Gym sends the chat call to its session's frontend. Today there is one URL; with this PR, Gym holds one URL per frontend (client_base_urls) and keeps each session on one of them.
  2. ② Our chat engine renders it with the checkpoint's template and splices the earlier turns from TQ. Today it is plugged in by patching Dynamo's main() (frontend.py, deleted). With this PR, Dynamo loads it through its supported --dyn-chat-processor flag (provider), and its settings arrive as one typed ChatProcessorOptions instead of four env vars.
  3. ③ That frontend's router picks one of the 4 engines. With several frontends, --router-replica-sync shares in-flight requests between the routers (in kv mode).
  4. ④ The engine generates and writes the call to TQ, the same in both columns.
  5. ⑤ The reply goes back through the same frontend to Gym.
  6. ✂ At a checkpoint, Gym posts its in-flight calls. Today that goes to a second port (a uvicorn thread), because Dynamo 1.5.1 routes could not take a POST, so RL had to pass Gym a second URL list. With this PR, the cut uses the frontend's own port as a routes() extension. The native and Dynamo routes now share one check-and-answer helper, answer_generation_cut.

Why the change is needed

What the review asks

No blocking bug. The design is a step forward: two patches of Dynamo's code become supported hooks, four env vars become one typed options object, and the native and Dynamo cut routes share one helper. The review asks for one small fix, one docs row, and evidence and tests for the new multi-frontend setup.

So what. This PR is what lets a 0.5M-rollout run use Dynamo at all: the session table no longer caps out at 65,536, and routing and rendering spread over the GPU nodes instead of one process on the driver's node. It also deletes two patches of Dynamo's code. Before merge: pin the Dynamo 1.8.0 release, and run two frontends on two nodes with numbers (C18), since even the default setup now puts the frontend on a GPU node.
