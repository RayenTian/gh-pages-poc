Two pages on this PR, one question each. This one: what the PR changes compared with PR 3.

Background. A prefill engine reads the prompt and keeps its KV blocks pinned until a decode engine has pulled them. A refit suspends every engine, copies the new weights in, and resumes them. Engines run the persist KV mode, so suspend and resume leave the KV memory, the block allocator and the pinned blocks alone. Dotted words have a short explanation: hover or tap them.

Example fleet: 1 prefill engine P0 and 2 decode engines D0, D1. Each row is one operation in MegatronDynamoGeneration, PR 3 on the left, this PR on the right. Boxes in one column run at the same time; arrows mean "then".

The same change as pseudocode

Refit suspend · driver process

# driver, MegatronDynamoGeneration.suspend_for_refit
call_engines(all engines, suspend)                     # PR 3: one wave
call_engines(prefill, suspend)                         # each wave: Ray calls in parallel
call_engines(decode, suspend)                          # no wait for pinned blocks
on failure: resume every engine the suspend reached       # then re-raise

Shutdown · driver process

# driver, MegatronDynamoGeneration.shutdown
for engine in engines: stop(engine)                       # PR 3: index order
owners = read handoff owner from each decode rank 0      # ≤600 s
for d in decode: stop(d)                                  # one at a time
for owner in owners:                                      # C3: one Ray call per owner
    prefill0.confirm_decode_terminated(owner)             # ≤ 600 + 10 s each
for p in prefill: stop(p)                                 # frees every pinned block anyway
stop frontend, NATS, etcd

Real code: PR 3 shutdown, PR 4 shutdown, _confirm_decode_terminated.

The 600 s is today's default dynamo_cfg.control_timeout_s. C1 removes that key (following #4801 C9), so the caller's timeout or a fixed shutdown constant takes its place. The problem does not depend on the number: each report still waits its full timeout, one after another.

🔴 review comment C3 — dynamo_generation.py:1381

Left behind: a pause for a wait that is gone

An earlier commit in this PR paused prefill, waited for decode to pull every pinned block, then suspended. A later commit (ef48e301) removed the wait, because with a deep decode backlog the pins did not drain for over an hour. The worker pieces stayed: pause_for_refit, a paused flag read in four places, and pinned_handoff_block_count. Only tests call them, here and in PRs 5 and 6. The class docstring, the PR title and the PR body still describe the wait.

The fix changed after the review of PR 2. #4912 C7 asks PR 2 to rewrite the worker's _sleep/_wake: every wait for an engine state gets a timeout, and wake looks at the engine's real state instead of a saved flag. So C4 asks this PR to take PR 2's version of those four functions as it is, not to restore the older untimed one or keep this PR's own change to when the flags are set.

🔴 review comment C4 — megatron_worker.py:2492 C5 — dynamo_generation.py:307 C6 — PR body

Will this hold up at 1,000 engines?

Take 500 prefill and 500 decode engines. vLLM, plain Megatron and TRT-LLM's own prefill/decode mode on main each keep every engine's workers in one worker group, so each step is one wave: send the call to every worker, then wait once (run_all_workers_single_data, TRT-LLM P/D wake and sleep). A wave costs as long as its slowest engine, however many engines there are. This PR keeps one wave for the weight transfer, the KV rebuild and the resume: _call_engines sends every call before it waits on any. Three steps don't:

🔴 review comment C9 — suspend in one wave C10 — build at once C11 — stop every engine at once

So what. The refit order is safe: upstream Megatron-LM keeps a suspended prefill engine serving pulls and releases in persist mode, and records the weight version per token. For the same reason it doesn't need to be an order at all: suspend can be one wave, like resume. The PR should drop the shutdown report step (C3) and the leftover pause code (C4), and fix the docs (C5, C6). At 1,000 engines the real cost is startup (hours, in rounds of 8) and shutdown (one engine at a time); startup should be one wave, and so should shutdown, as on main.
