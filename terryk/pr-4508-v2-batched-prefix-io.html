What changes when prefix saves and restores go to TransferQueue in batches, and what the rebase onto Dynamo breaks

Before
At a checkpoint, each unfinished model call saved its tokens with its own TransferQueue write. After a restart, each resumed request read its own saved rows on its own thread.
This PR
Groups the saves into a few large writes, and merges the reads of requests that resume together into one shared read. Two config keys set the batch limits.

Four pages on this PR. The round-1 pages describe an older head. This one: how the batched path differs from the old one, and what the Dynamo rebase does to it.

Background. When RL saves a checkpoint in the middle of generation, each unfinished model call writes its tokens so far to TransferQueue (TQ), one row per call. After a restart, Gym sends the call back with the keys of its saved rows, and the call continues from them instead of starting over. Dotted words have a short explanation: hover or tap them.

Before, the save loop wrote one call at a time (_cut_active → stage_generation_prefix). Now _cut_batched freezes calls one by one, keeps each locked, and writes up to 256 rows in one stage_generation_prefix_batch call. On restore, the new PrefixReadBatcher waits 2 ms, merges the keys of every request that asked, and runs one get.

The two paths, on one small example

Example: 3 unfinished calls (c0, c1, c2) and a batch limit of 2 rows. On restore, c1 has 2 saved rows (one from an earlier checkpoint), so the 3 requests need 4 keys.

Both write paths build a row with _encode_record, the old single-row body moved. The per-call freeze, ack and seal logic is the old body too, now the generator _cut_transaction, so a batch can keep several calls frozen at once. Both restore paths end in resolve_restore, which checks the prefix digest and lets the call regenerate if anything is wrong. A call that finishes while its group's put runs waits for its lock (asked in the review body). A failed group put is retried one row at a time, so a bad row fails only its own call.

What each piece does: resolve_restore now does the shared read itself, so no caller can skip it. Any read failure, including a wrong-loop call, reaches the existing except: a WARNING, and the call regenerates. Before, a DEBUG log hid it and the rows were read again. The chunks= argument, _fetch_chunks and read_restore_chunks go, about −25 source lines. The return type stays the same, so the routes from #4612 C27 and the media from #4979 C92 ride on the same object. About 8 test calls gain await. C14 replaces the two fallback tests with one test of 4 concurrent restores through resolve_restored_call that asserts one read, plus one log grep in the prefix-recovery functional script, which also runs behind Dynamo. So what. The batching itself is sound and reuses the old code well. But its restore half hangs on one call site that the Dynamo rebase deletes, and nothing would notice: restores would quietly go back to one read each. Moving the read into resolve_restore fixes that for native and Dynamo at once, and makes the PR smaller. The other size cuts are on the what can shrink page.
