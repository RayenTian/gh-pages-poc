What happens to 5 ready groups on 3 training ranks — on main, and with this PR

NVIDIA-NeMo/RL #5248 · issue #5240 (item 1) · permalinks pin head b52f74b

Before
A streaming GRPO chunk was every ready group. If its sample count did not divide by the number of training ranks, the step crashed before training started.
This PR
Setup works out the smallest group count that always divides evenly, and the sampler takes only whole multiples of it. The other groups wait for the next chunk.
Status
Fixed by this PR for the normal case. One end-of-data case is still open — see page 2.

Two pages on this PR, one question each — this one: how a chunk is split across ranks, before and after.

Setup for the whole page. GRPO, streaming: the trainer trains on prompt groups in chunks as they finish generating. 5 groups (A–E) are ready, with 2 samples each, so 10 samples. The policy has 3 DP ranks, and sequence packing is on with 1024 tokens per microbatch. The number after each sample is its token length. Every result below is a real run of the repo's own code. Dotted words have a short explanation: hover or tap them.

Your picture vs. what main actually does

The natural guessWhat main does
What is splitGroups: 2, 2 and 1 group per rankSamples. A group's two samples can land on different ranks.
10 samples on 3 ranksOne rank gets fewer, or is paddedNo padding. shard_by_batch_size first asserts that the sample count divides by the rank count. 10 ÷ 3 does not, so it stops there, before packing runs.
Microbatches per rankDifferent after packing, e.g. 3 / 2 / 1Always the same on every rank. The packer rounds its bin count up to a multiple of the rank count (bin_count_multiple=shards), moving real samples into the new bins rather than padding (_adjust_bin_count), then deals bins round-robin (bin i → rank i mod 3). Token counts per microbatch differ; the count does not.

The other two modes keep the count equal too. Dynamic batching sizes each microbatch by the longest sample at that position on any rank (the code says this "is required for Automodel and megatron policies"). Static batching uses a fixed train_micro_batch_size, so each rank's sample count must also divide by it.

5 groups on 3 ranks: main vs. this PR

What the PR changes, as pseudocode

Before (base 9a7640c)

# train pump (async loop on the controller)
kwargs = {}                                      # GRPO: no size rule
chunk = sampler.select(min=floor, max=left, **kwargs)  # 5 groups = 10 samples
trainer.train(chunk)                               # split asserts 10 % 3 == 0 → crash

After (head b52f74b)

# setup, once, when the trainer is built
m = resolve_grpo_chunk_alignment(cfg, dp=3)       # m = 3; rejects a step size or cap not divisible by m

# train pump (async loop on the controller)
kwargs = {}
if m > 1: kwargs["group_multiple"] = m
chunk = sampler.select(min=floor, max=left, **kwargs)  # 5 ready → A, B, C; D, E wait
trainer.train(chunk)                               # 6 samples → 2 per rank

# same pump, when no chunk can be selected
if data_exhausted and len(buffer) < m: return   # a tail below m is not trained

The split itself is unchanged; the PR only controls how many groups reach it. Real code: setup.py L2040-2042, _train_pump L2801-2810, is_last_step L3758-3761.

Where the fix lands: RL only. Setup (config.py, setup.py) computes m once; the train pump passes it to the sampler, which already knew how to round down (PPO used it first). Sharding and packing are untouched.

Still open (both are review comments):

  • End of data with dynamic sampling. A step whose target shrinks to a number that is not a multiple of m still crashes, now in the sampler. Page 2 shows it and the one-line fix. review comment C1 · single_controller.py:2810
  • weight_fifo streaming can now hang. That sampler only takes groups from the oldest weight version, so a leftover group there can never fill a multiple. Before the PR this failed at once; now it waits for the stall watchdog. review comment C2 · config.py:2035
  • A step that loses a prompt. With a drop budget and on_dropped_prompt: shrink, a step of 18 that loses one prompt has 17 groups. With a multiple of 3 it crashes in the sampler (main crashed too, at the split). Rounding every shrunk step down to a whole multiple — 15 here — lets min_step_batch_fraction decide whether it trains or stops cleanly. review comment C5 · config.py:2012
So what. On main, a streaming GRPO chunk crashes whenever the ready sample count does not divide by the DP size. Packing does not save it, because the even-split check runs first. With this PR the chunk is always a whole multiple of m groups, so the split always succeeds. The cost is that up to m − 1 ready groups wait one more chunk, and at the end of data a tail smaller than m is not trained.
