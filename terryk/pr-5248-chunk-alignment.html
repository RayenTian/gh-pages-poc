Why a GRPO training chunk now takes 20 of 21 ready groups

NVIDIA-NeMo/RL #5248 · issue #5240 (item 1) · permalinks pin head b52f74b

Before
A streaming GRPO chunk was as many prompt groups as happened to be ready. A count that the training ranks could not split evenly crashed the step.
This PR
Setup works out the smallest group count that always splits evenly, and the sampler takes only whole multiples of it. The rest wait for the next chunk.
Status
Fixed by this PR for the normal case. One end-of-data case is still open — see the second page.

Two pages on this PR, one question each — this one: what the PR fixes and how.

Background. In streaming GRPO the trainer does not wait for the whole step. It trains on prompt groups in chunks as they finish generating. Each chunk is split evenly across the data-parallel (DP) ranks, and that split does not allow one rank to get more samples than another. Dotted words have a short explanation: hover or tap them.

The trainer splits each chunk with shard_by_batch_size, which raises if the sample count is not a multiple of the DP size. Before this PR, GRPO gave the sampler no size rule, so with 16 answers per prompt on 32 DP ranks, a moment with 21 ready groups made a chunk of 21 × 16 = 336 samples — 10.5 per rank. The PR adds resolve_grpo_group_multiple: the smallest group count whose samples always split evenly. Here that is 32 ÷ gcd(32, 16) = 2 groups, so every chunk is an even number of groups.

Same 21 ready groups, before and after

The change, as pseudocode

Before (base 9a7640c)

# setup, when the trainer is built
validate_grpo_chunk_cap_alignment(cfg, dp)  # checks only a full chunk at the cap

# train pump (async loop on the controller)
kwargs = {}                                  # GRPO: no group_multiple
chunk = sampler.select(min=floor, max=left, **kwargs)  # any size: 21 groups
trainer.train(chunk)                         # 336 samples → split raises

After (head b52f74b)

# setup, when the trainer is built
validate_grpo_chunk_cap_alignment(cfg, dp)
m = resolve_grpo_chunk_alignment(cfg, dp)    # m = 2; raises if step size or cap % m != 0
                                              # warns if drop budgets > 0

# train pump (async loop on the controller)
kwargs = {}
if m > 1: kwargs["group_multiple"] = m
chunk = sampler.select(min=floor, max=left, **kwargs)  # 21 ready → 20; 1 waits
trainer.train(chunk)                         # 320 samples → 10 per rank

# same pump, when no chunk can be selected
if data_exhausted and len(buffer) < m: return  # tail below m is not trained

Real code: setup.py L1997-1999, _train_pump L2796-2805, is_last_step L3753-3756.

Where the fix lands: RL only. Setup (config.py, setup.py) computes the multiple once; the train pump passes it to the sampler, which already knew how to round down (PPO used it first).

What is still open

The review found two cases the fix does not cover yet. Both are comments on the review.

  • End of data with dynamic sampling. A step whose target shrinks to an odd number still crashes with No multiple of 2 fits selection bounds. The second page shows it and the one-line fix. review comment C1 · single_controller.py:2810
  • weight_fifo streaming can now hang. That sampler only reads groups from the oldest weight version. If one group is left there, it can never make a pair, and the step never closes. Before the PR this failed at once; now it waits until the stall watchdog fires. The fix is to reject this setup at startup. review comment C2 · config.py:2035
So what. A streaming GRPO run can no longer crash mid-step because "too many" groups happened to be ready at once. A config that can never split evenly is now rejected at setup, not partway through a run. What you give up: up to m − 1 ready groups wait one more chunk, and at data exhaustion a tail smaller than m is not trained.
