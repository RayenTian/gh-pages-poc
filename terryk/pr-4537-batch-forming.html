Five pages on this PR — this one: what a shared-prefix batch looks like, step by step.

Background. In GRPO each prompt gets several sampled completions, called a group. Before a training step, the policy runs a forward pass over every row to get log probabilities, then trains on them. Rows are packed into forwards under a token budget, and the batch is split across data-parallel ranks. Dotted words have a short explanation: hover or tap them.

The example: 4 prompts (A–D, 80–120 tokens) with 3 completions each, 12 rows, 1655 tokens. Data-parallel size 2, token budget 600, no tensor or context parallelism. The figure is real planner output: #8152's planner, run on CPU on these lengths with the settings the PR requires at data-parallel size above 1 (pack_groups and align_data_parallel on, everything else default).

The steps, with the example's data

  1. The rollout records where each prompt ends. One number per row, e.g. row A0 → 120. Group identity is the existing group tag. rollout_reassembler.py
  2. The trainer takes whole groups, in multiples of the rank count. 4 groups ÷ 2 ranks. single_controller.py
  3. The driver gives each rank whole groups, longest first, to the lightest rank. Full group lengths A 460, C 425, B 395, D 375 → rank 0 gets A and D, rank 1 gets B and C. preshard.py → plan_group_coherent_shards
  4. Each rank cuts each group into slots by full row length. A slot holds at most 16 rows whose full lengths fit the budget. Group A (460 ≤ 600) stays one slot. A group longer than the budget is cut into several slots, and each slot computes the prompt again. shared_prefix_execution.py
  5. Each slot whose rows share one prompt becomes a star. Two stars share a forward only if their full lengths together still fit, because the model's multi-token-prediction head runs on full rows. A + D is 835 > 600, so they stay apart. the full-length check
  6. All ranks agree on the forward count in one all-reduce. If a rank has fewer, real rows are split to make up the difference. No dummy rows are added, and a planning error on one rank travels in the same all-reduce, so every rank raises. megatron_policy_worker.py
  7. The model runs the star. Each completion attends to its prompt and its own earlier tokens, never to a sibling. train.py · model_forward → Megatron-LM attention
  8. Log probabilities are copied back into the usual [rows, S−1] tensor (rows × token positions), and the GRPO loss runs unchanged. train.py · shared_prefix_next_token_logprobs

An optional mode, training_dense_bins, plans the other way round: it packs full rows into bins first, then shares prompts inside each bin. Groups then split across forwards, and a bin of single rows runs dense. The same example takes 1255 tokens that way. share_prefixes_in_dense_training_bins

A long row can force a second forward that computes the prompt again. The planner cuts each group into slots by full row length (shared_prefix_execution.py#L272), so a row that does not fit next to its siblings runs in its own forward, with its own copy of the prompt:

How a rank plans its forwards, as pseudocode

# Megatron worker, once per training call (before: no planning, one packer) bins = pack(rows, budget=600, length=full_len) # dense today: 12 rows → 2 bins per rank slots = [] for group in rows.by_group(): # A, D on rank 0 slots += first_fit(group, budget, length=full_len, max_rows=16) # A: 460 ≤ 600 → one slot stars = [star(slot) for slot in slots if same_prompt(slot)] # A star: 120 + 50 + 30 + 20 = 220 fwds = merge(stars, budget, also_full_len_fits=True) # A + D full = 835 > 600 → 2 forwards n = all_reduce_max(len(fwds)) # every rank runs n forwards fwds = split_real_rows_until(len(fwds) == n)

Inside one shared forward (rank 0, forward 1)

# rows A0, A1, A2 → one star, 220 tokens instead of 460 node 0 1 2 3 is A prompt A0 A1 A2 node_start 0 120 170 200 node_len 120 50 30 20 parent -1 0 0 0 # -1 = the root; every completion hangs off the prompt position ids A prompt 0..119 · A0 120..169 · A1 120..149 · A2 120..139 # every branch restarts after the prompt A1 attends to A prompt + A1's own earlier tokens # not A0, not A2 row A0 logprobs cols 0..118 = prompt predictions (computed once, copied to A0, A1, A2) cols 119..168 = A0's own; col 119 (A0's first token) is predicted from the last prompt token

Source: PackedTreeLayout stores start, length and parent per node, and computes positions. These numbers are the planner's real output for group A. Mamba layers copy the recurrent state at a chunk boundary inside the prompt into each branch, then replay the rest of the prompt per branch; see the Megatron-LM doc.

Where the two paths meet, and what still differs

Both paths end at the same loss: a [rows, S−1] log-probability tensor with the same masks and the same token counts. They differ before that point in three ways:

  • Which rank gets which rows: dense scatters a group, shared keeps it on one rank.
  • How many tokens each forward computes: 855 instead of 1655 here, in the same number of forwards.
  • How the numbers are added up: shared and dense are both valid arithmetic, but in BF16 their gradients are not bit-identical. The PR's design doc measures that difference and says it is still open.
So what. With the default settings, shared mode keeps every group in one forward and computes each prompt once: 855 tokens instead of 1655 here. It still runs the same number of forwards as dense, because the budget also counts every row at full length, so each forward is less full. Raising the budget to 3× (1800) puts A and D in one forward: one forward per rank. The PR's large-scale run changed the budget and sharing at once, so its speedup mixes the two effects. A failed-rollout placeholder row (prompt length 0) cannot share, and runs dense.
